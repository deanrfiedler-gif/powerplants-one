---
title: Remaining phone identity changes on record pages wait for the record row
date: 2026-10-29
---

PR #736 made the P05 and P06 browser tests wait on phones for the record row (`#shell-header[data-phone-header="record"]`) before they change the identity through the phone menu ([earlier fragment](2026-10-28-phone-menu-identity.md)). Until a record page's own read returns, its phone header shows the list row with Menu on the left. The read then replaces Menu with Back. A press that starts on Menu as it is replaced reaches nothing, so the "More" dialog never opens. That fragment listed the sites still open. Dean asked on 28 October for the same treatment at the remaining sites with this race. Every site was checked against current main (dc32160b5, after #741, #742 and #743).

- **Finding the sites.** A local-only survey instrumented every page, including the contexts that tests open themselves. It logged each press on the header Menu, which row was showing, and whether the record row replaced Menu within 5 s with no identity change in between. The survey ran on main af079a2f over the full mobile-chromium suite (649 tests), the three P11 specs alone, the `tests/scheduling-browser` suite on mobile, and six desktop specs that narrow to phone widths. Menu was pressed 119 times. In 117 of those presses the row stayed the list row until the identity changed: list pages, pages without a record row, and pages whose read the identity then in effect could not complete. In two, the record row arrived afterwards (43 ms and 82 ms later). Those two are the sites changed below. Every other identity change either did not use the menu, or found the record row already in place and used the tab bar's More. The 23 commits between af079a2f and dc32160b5 add no identity change and do not change these pages: they changed `reports.spec.ts` only in steps that follow its identity changes, repaired `tests/helpers/quality-keyboard.ts`, and added Supply and communications server code.
- **Changed: `tests/browser/reports.spec.ts`, FI07 native attendance test (line 991).** After an offline replay, the assigned technician opens the report and the test changes to the coordinator. On phones it now waits for the record row first, with #736's comment.
- **Changed: `tests/helpers/quality-return.ts`, `prepareReturnVisit`.** This is the only caller of `quality-browser.ts`'s `identity()` (and so of `openIdentityControls`, which presses Enter on the same opener) that runs straight after a record page opens. All three of its callers open the source report first: the P11 journey's return device (`service-journey.ts:745`), the Step 6 journey (`tests/step6-browser/journey.spec.ts:191`) and the desktop acceptance journey (`tests/acceptance-browser/journey.spec.ts:66`, where the phone guard leaves it unchanged). The wait therefore sits once, just before that `identity()` call. The shared helper is unchanged and gains no parameter, because it is also called from list pages and from pages whose read is refused.
- **Not changed: `tests/browser/work-orders.spec.ts:92`.** This `identity()` is the test's first, in a fresh browser context. With no session the page renders no records and the identity selector is already showing, so the phone menu is not used. A record-row wait there would never end. The #736 harness measured this route with a session already chosen, which the test does not have.
- **Not changed: `tests/browser/email-calendar.spec.ts:173`.** The email detail page never shows a record row, so Menu is never replaced and a wait would never end. The test narrows to 320 px on desktop-chromium too, and the desktop survey saw the same.
- **Other `quality-browser.ts` callers in the P09–P11 journeys.** `quality-prepare.ts:620` and `:673`, `service-journey.ts:89`, `:113` and `:569`, and `quality-return.ts:70`, `:213` and `:485` pressed Menu on rows that never become record rows: personal job pages, or a finance handoff or report that the identity then in effect cannot read. The fifteen screen families in `quality-states.spec.ts` change identity while each page's read is failed or held, so no record row arrives. `quality.spec.ts` changes identity on list pages and on a recovery page without a record row.
- **Not run.** The Step 6 suite is run by the owner and is not in CI. Its other identity changes come before a `goto` or after the report content is visible. The acceptance journey is desktop-only. `tests/ui/crm-board.spec.ts` uses a static board fixture.

Harness: the #736 harness was extended to one call site: the identity in effect, then the record route, then the identity change through the spec's own helper (a pointer click, or Enter for `quality-browser.ts`). Counts are lost presses out of iterations. The dialog never opened in each lost case.

| Site | Main af079a2f, without the wait | Main dc32160b5, without | dc32160b5, with the wait |
|---|---|---|---|
| FI07 report (technician → coordinator, click) | 1 of 200 (162 presses on Menu; the lost one had the row change between pointer down and up) | 2 of 200 (136 on Menu; both lost presses changed row mid-press) | 0 of 200 (every press on the tab bar's More) |
| P11 return report (coordinator → coordinator, Enter) | 2 of 200 (147 on Menu; in the 2 lost, Menu was focused then replaced before the keydown, so Enter reached the page body) | 3 of 200 (149 on Menu; 3 of the same kind) | 0 of 200 (every press on the tab bar's More) |
| Work order, fresh context (as at `work-orders.spec.ts:92`) | 0 of 30, with no menu press in any; with the wait, it timed out in 3 of 3 | not rerun | not applicable |
| Email detail (coordinator → Systems) | 0 of 30, with 30 presses on Menu and no row change in the whole log; with the wait, it timed out in 3 of 3 | not rerun | not applicable |

On af079a2f, the two changed sites also measured 0 of 200 with the wait, with every press on the tab bar's More.

Checked locally on 29 October 2026: Linux container, compiled application (`npm run build` of this branch on dc32160b5), disposable PostgreSQL 16 `ppo_synthetic_test` restored before each spec run from a fresh migrate and seed (120 migrations), with `max_locks_per_transaction=256` as `scripts/configure-test-postgres.sh` sets in CI. Chrome 156 is not installed. The browser and the server's document renderer used the pre-installed Chromium 153.0.8010.12 through a local-only override, which is not committed.

- With the change on dc32160b5, mobile-chromium passed `reports.spec.ts` (4 tests), the P11 journey `quality-journey.spec.ts`, `quality-states.spec.ts` (6) and `quality.spec.ts` (4). Desktop-chromium passed `reports.spec.ts` and the P11 journey.
- The harness runs on dc32160b5 started from a copy of the database after the desktop run, which holds the reports they open.
- `npm run lint`, `npm run typecheck`, the unit tests (1,279 passed), `npm run build`, `npm run studio:check`, `python3 scripts/check_foundation.py`, `python3 scripts/check_prototype.py`, `python3 scripts/check_naming.py`, `python3 scripts/build_status.py --check`, `python3 scripts/check_migrations.py`, `python3 scripts/ci_scope.py --self-test`, the documentation unit tests and `python3 scripts/check_documentation_scope.py --base origin/main --head HEAD` passed.
- Not run: the Chrome 156 channel that CI uses, a full-suite run with the change, the Step 6 and acceptance suites, and the other browser lanes.
- Before #741's keyboard date repair, the P11 journey failed locally on af079a2f at its keyboard booking move, because the booking day and the moved day fell in different months (on 29 October in Brisbane, Friday 30 October and Monday 2 November). The survey reached its later identity changes with a local-only shift of the test-side visit date. On dc32160b5 the journey passed unaided.

Open:
- A person who taps the top-left control just as a record loads can still lose the tap, or reach Back instead of Menu. The shell notes describe the list row before the record loads as intended, so any change there is a design decision.
