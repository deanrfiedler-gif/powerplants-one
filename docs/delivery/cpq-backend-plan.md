## Boundaries in this backend

Release revisions currently seal facts, component descriptions, rules, constraints, price tiers and fixtures as one JSON definition. This is a governed native core, not the complete normalized CCE authoring architecture. Schema 1/3 fixture component keys are not published Products variant identities. Opt-in schema 2 binds selected components to exact published native Variants and freezes technical/publication/conditional-relationship evidence; existing authored prices are unchanged. Input values are explicitly supplied by an authorized estimator; discovery is frozen as provenance, but automatic semantic mapping is not invented. Prices are synthetic AUD, excluding tax; sell below cost is refused by the existing native policy. No production rules, source feeds, discounts or currency conversions are supplied.

Rule evaluation supports typed ALL/ANY/NOT comparisons and material/labour contributions. SUM, MAX, UNIQUE and PRIORITY resolve a target within an equipment instance. Equal winning priorities are conflicts. This does not implement global configuration search, cascading derived-fact graphs, general decision-table authoring or capacity optimization. Those require the P1/P2 contracts above.

All requests are online. Runs are immutable results rather than durable asynchronous jobs; evaluation occurs in an isolated worker while the existing workspace transaction serializes mutations. A five-second budget and bounded definitions suit the synthetic prototype, not an enterprise throughput claim. Move execution to a durable queue, add quotas/cancellation and revalidate the snapshot after completion before increasing workloads.

## Integration order for Claude

1. Build the release register and immutable revision view against scoped reads. Add structured editors that produce the published definition shape; avoid a raw JSON editor as the final user experience.
2. Connect the test bench, review and publish actions. Display exact hashes/revisions in an evidence drawer; ordinary screens use meaningful names, states and dates.
3. Launch CPQ from the selected Complete discovery option. Fetch a basis and render the release's typed facts for stable instance IDs. Clearly distinguish imported evidence from entered assumptions.
4. Calculate and show Ready/Blocked results, including all diagnostics. Present totals as AUD excluding tax, and render “Why this line?” from retained contributions.
5. Recalculate after input/override changes; preserve the parent run and user reasons. For changed override bases, require explicit review before using the new basis hash.
6. Show native receiving preview, retained lines and generated replacements. Require exact confirmation before adopting; then navigate to the returned native estimate and existing review flow.

## Release evidence and remaining decisions

Record actual test results in the PR and STATUS. Backend tests are implementation evidence, not operational approval or UI acceptance. No merge, deployment, production migration or Figma edit is part of this workstream.

Owner decisions needed before P1 acceptance: first operational equipment family; technical fact/constraint owner; approved price and labour sources; margin/discount authority; user roles; realistic maximum instance/line counts; and performance/service targets. Work on typed contracts and synthetic tests can proceed before those decisions; live policies cannot be guessed.
