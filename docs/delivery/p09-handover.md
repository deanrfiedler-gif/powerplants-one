## Delivered implementation and authority

[ADR-0014](../decisions/ADR-0014-p09-service-reports.md), [physical dictionary](../contracts/service-data-dictionary.md#p09-physical-implementation-amendment), [API amendment](../contracts/service-api.md#p09-physical-command-and-read-amendment) and [OUT-10 contract](../contracts/document-issue-distribution.md#p09-controlled-out-10-implementation) define the implemented records and commands. These supersede conceptual future-tense P09 descriptions without changing historical P07/P08 delivery evidence.

P09 implements SC-11, DAT-09, bounded OUT-10, API-C16–18 and TR-11–13. Completion drafts remain separate from immutable submissions. Every actual technician attendance has its own report and exact evidence/declarations; another person cannot submit on their behalf. The appointment moves InProgress → CompletedPendingReview on first submission and Completed only after all actual attendances are accepted. Return needs no new physical start. Accepted attendance remains immutable through report-only correction. New physical work requires existing P04/P05 return/new-visit authority. Work-order/ticket/Finance closure remains independent and unimplemented at this increment.

Service owner review decides every exact entry, retains internal reasons and returns corrections to the original technician. Approved quantities are the captured quantities of those exact versions; no financial treatment is inferred. Partial/UnableToProceed preserve tasks, uncertain asset identity, failed fixes, unresolved controls and owned follow-up. Scope/pack change requires explicit original-attendance-only disposition; it cannot waive mandatory controls or make incomplete work Complete.

Report HTML/PDF are rendered from the exact reviewed allowlisted customer projection, named permitted site contact and template. Private bytes are durably verified before final release. Original job recovery reconciles storage success/database failure; stale source/template/audience retains an owned attempt. Old outputs are never regenerated, overwritten or signed in place. HTML presentation hashes and separately retained PDF hashes remain explicit. Five response alternatives bind exact HTML presentation/revision/kind; optional synthetic PNG marks remain protected and cannot transfer to changed content. Customer response is not Finance approval, independent identity verification, whole-project acceptance or real delivery.

Report revisions and P07 entry versions are distinct. Report review stores its own decision projection over exact entries; it does not relabel or overwrite the P07 original factual row. Captured and reviewed quantities are preserved without rates, billability, warranty, payroll, rounding, breaks or stock inference. Accepted attendance ends cannot be changed by report-only corrections.

Additional captures are frozen while Submitted/Reviewed/Issued. A stale or competing return/approve/issue/correction command fails its expected version or exact-set check. Scope/pack changes cannot transfer authority; OriginalAttendanceOnly records historical review, and changed authority cannot approve a Complete claim. Incomplete time/material declarations remain explicit in Partial/UnableToProceed review and output, with reasons/blockers and owned next action; they do not claim missing quantities or future Finance readiness. Complete remains blocked. Partial/UnableToProceed require remaining work and an eligible existing service owner. Return proposals use the existing work-order visit proposal UI/API; a proposal does not reserve or confirm a booking.

Each presentation is separately identified. DraftEvidence HTML is retained from approved review; IssuedReport HTML and PDF come from the durable bundle. The response hash binds the HTML actually shown in the embedded customer presentation; the issue separately retains the exact PDF hash. No PDF presentation or independent signer verification is implied. Old report retrieval remains possible within current scope, but an old presentation cannot receive a response after a new correction cycle begins. A prior signature hash cannot be reused on materially changed presented content, even by uploading the same mark again.

## Permissions, original-operation recovery and limits

Current workspace membership, company/site permission, appointment assignment or service-work access and report capability are rechecked by server-derived identity. Review and issue additionally require the current work-order service owner. Technicians submit/amend only their own actual attendance. Systems identity is not report authority. Receipt recovery reauthorises the original command's current capability and record scope; a response receipt additionally remains bound to its capturing actor.

An uncertain online mutation retries the same operation ID and unchanged payload or reads its original receipt through the existing operation route. Changed operation-ID reuse is refused. An uncertain render uses its original owned job's **Generate / recover original report** action or the bounded document worker. The operation's original durable bundle is located and verified; it is not rerendered if already stored. Failed and StaleSource attempts keep owned recovery and immutable attempt history. A source/template/audience change requires a successor review cycle. Missing/wrong-hash issued bytes make the exact document unavailable, retaining the issue reference; no replacement bytes are generated.

The worker uses a recoverable two-minute claim and at most five jobs per invocation. Final issue, audit, receipt, outbox completion and distribution task share one database transaction. A late database failure leaves the original stored bundle recoverable without a second issue or distribution task. Response PNG storage uses the exact original operation, report presentation and content hash; database rollback can reconcile those same bytes without a second signature object, response or follow-up. Rendering itself, retrieving a file and recording a contact outcome are separate from issuance, acknowledgement and real delivery.

Customer HTML/PDF, public manifests, generated previews, report cache entries and response-mark routes expose only their intended content. Internal review comments, Time notes, stock-status/source-reference fields, unrelated filenames, Finance fields and private provider identities are excluded from customer output; the staff review screen retains authorised original facts needed for review. All private file routes require current authority and use no-store/nosniff policy. Private original storage remains the synthetic local adapter, not a verified SharePoint interface.
