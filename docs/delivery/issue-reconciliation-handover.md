## Delivered changes

The shared [UI specification](../standards/ui-style-specification.md) r07 now records the entire flex/grid scroll chain, reachable scroll ownership, sticky/frozen content, keyboard clearance and long dialogs. Its layer bands match the actual shell values (30–79 chrome, 80–119 menus/affordances), preserving nested stacking contexts and native dialog top-layer behaviour. The suggested 100/200 bands from #121 were proposals; documenting those as existing values would be incorrect. No CSS is renumbered.

The CRM worklist uses validated URL state for view, pipeline, search, company/site/owner, outcome, action state, stage filter, sort, page size and selected phone stage. Defaults are omitted. The existing Next search-parameter subscription observes native History API changes: criteria replace the current entry; view/pipeline/phone-stage navigation pushes one. This preserves search focus without a server navigation per keystroke. Duplicate or invalid controls fall back to safe defaults; unknown parameters confer no authority. Native History API support is already part of the installed Next runtime, so this introduces no dependency or routing technology.

Signed paging tokens stay in memory, bound to the criteria that produced them. Reload, a shared link, changed criteria or Back starts at page one. Identity lock and denial clear sensitive criteria; all reads retain the current server permission contract. No actor, operation, receipt, grant or proposed command enters the URL. Per-user saved views remain outside this issue. The synthetic CRM visual fixture supplies the equivalent search-parameter subscription so existing visual checks continue to inspect the real component.

New verification covers URL validation/round trips and real desktop/phone journeys through typing, filters, sorting, reload, copied tabs, canonical detail and Back, with unchanged business-table hashes and no command requests. A separate actor opens the copied URL and cannot see the original record; identity change clears the current criteria. Original images and source/tree/run/hash manifests are written by the existing capture helper.

Transfer verification adds observed PostgreSQL lock-order cases for designating an existing next Activity and for Activity completion, cancellation and reassignment racing transfer in both orders. It also exercises immutable provenance where creator differs from initial owner, multiple transfers surround qualification/planning, and a historical user is renamed/deactivated. These extend the existing suite without changing application permissions or writing a new migration. They are components of HV-06/08/22, not claims that every surface of those written procedures passed.
