## First slice and rationale

**I1 — Owned opportunity and qualification follow-up:** a synthetic sales owner selects an existing permitted organisation, creates an Open opportunity and a real owned next Activity, completes that action with an outcome, records qualification/progress and sees a new next action or the explicit need to plan one. Reload proves persistence. Another company/role cannot see or mutate it.

This yields a usable sales journey without relying on unknown operational pipeline names, source fields, pricing or mailbox configuration. It exercises the most consequential shared change—Opportunity links in Activity visibility/receipts—early and in a small surface. It is more valuable than disconnected account, board and report screens, and lower risk than beginning with migration, a separate lead model or Finance/quotation integration.

First slice uses one fixed, clearly fictional pipeline with Enquiry → Qualified and `close_outcome=Open`. Both states are stages of one Open opportunity, not Pipedrive entity conversion or customer acceptance. No money/probability fields. Existing CustomerContact/RelationshipReview kinds cover its manual action. This fictional choice is implemented only under the separate I1 instruction; it remains unrelated to owner acceptance of operational pipeline policy.

## I1 build contract

### Included data and commands

Use BP-03 sections 4–7 as design authority. Add `Opportunity` to existing identity/audit/receipt handling and OPP allocation using the current registry pattern; do not change accepted references. Fixed company/organisation/site/contact context avoids unsafe Activity relinking. Site/contact can be unknown with reasons. Synthetic owner grants are explicit, additive, once-only and do not revive revoked permissions.

CreateOpportunity creates the first Activity and link in the same transaction. RecordQualificationAndProgress permits Enquiry → Qualified only with need and a contact or an owned identification action. PlanOpportunityAction designates a permitted active linked action or creates one atomically. Existing Activity completion retains its current owner/outcome rules. If the designated action is terminal, read derives Next action needed until another active action is designated; this is never disguised as an upcoming completed task. No arbitrary Opportunity update/close/transfer endpoint is included.

Use normal synthetic navigation: My Work remains service/general work; add a clearly labelled CRM area with Sales worklist, New opportunity and Opportunity detail. Shared organisation/person/site pages remain canonical. A list view is sufficient; board interaction belongs to I2. Context pickers validate the same company/person boundaries server-side. Maintain online saved/unsaved/uncertain/conflict states, keyboard focus and responsive layout.

### Migration and compatibility obligations

Allocate the next migration/version/ADR against live main and open PR reservations; do not presume 0009 or ADR-0014 is free. Extend current full unions and dispatch, including any delivered P09 identifiers. Add real composite FKs and deferred target/link checks for Opportunity, including a designated Activity genuinely linked to that opportunity. Reject inconsistent company/site contexts and invalid linked identities through direct SQL tests as well as API validation.

Fresh database and upgrade from the then-current accepted baseline are separate cases. Preserve old migration/seed/reference bytes, existing grants, IDs, versions, operation hashes/receipts, immutable evidence and unsent P08/P09 payloads. Repeat seed cannot overwrite edits, resurrect grants, reset counters or duplicate activities. Explicit disposable reset remains guarded. No import/runtime Pipedrive adapter is added.

### I1 done boundary

The journey persists and is usable on desktop/phone; authorised/denied direct/list/selector/Activity/receipt paths are tested; real database competing transactions and HTTP retries/revocation pass; source/delivery evidence is reviewable. Existing P01–P09 behaviour is preserved **as actually delivered at the verified baseline**, not assumed complete from a branch name. Full repository CI runs unchanged unless an explicitly necessary compatible extension is made in the implementation session. Full AT-25 stays Planned until its accepted inventory and complete scenario are executed. Prepare I2's bounded starter, then stop.
