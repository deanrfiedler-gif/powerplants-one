# ADR-0012 — P07 online technician evidence

**Date:** 5 September 2026 · **Status:** Implemented and component-verified; exact publication evidence in the P07 handover. No independent review, owner acceptance or production-readiness claim. **Scope:** issue #32, SC-09/10, DAT-08, API-C12–14, online TR-09/10, PT-06 integrated and PT-13/14 components.

Keep the pinned TypeScript/Next.js/PostgreSQL stack and shared workspace transaction lock. No dependency upgrade is required. Each assigned technician records their own start, with a separate immutable authority snapshot and server receipt time. The appointment's first actual start changes its state to InProgress; it creates no other person's attendance or labour. Additional crew starts repeat current P06 readiness inside the same transaction. Current resource effectivity and competency must span actual receipt time through the later of receipt or planned end; future-booking eligibility alone is insufficient. Ordinary P05 move/cancel commands continue to refuse started work. Scope changes and pack withdrawal retain evidence and hold further work; already-started technicians can record what happened against their original authority, visibly requiring review. This is evidence capture, not renewed authority to act.

Preserve relational appointment, actor, assignment, scope, issue and entry references. Versioned, strictly validated discriminated payloads implement six field types. Accepted capture has Draft review status; its Captured receipt denotes persistence only. Immutable successor corrections retain the original payload and authority. A separate current-time projection has a PostgreSQL half-open exclusion constraint per actor across all appointments. Corrections atomically replace only that projection. There is no overlap override, payroll rounding, automatic break deduction or billing conversion. Quantities and numeric readings use bounded canonical decimal strings, preserving exact decimals. No item catalogue is invented; material references remain Unknown or ReviewRequired. Required/Removed materials and unresolved findings/checks create owned service follow-up using existing Activity/ActivityLink support.

Use the P06 private write-once synthetic byte adapter. The initial media policy accepts a deliberately bounded PNG subset: non-interlaced 8-bit RGB/RGBA, at most 4 MiB, 4096 pixels per dimension and 12 million pixels. Check signature, chunk ordering/length/CRC, decompression limits, exact scanline size and filters; reject animation, embedded text/EXIF and unsupported chunks. Metadata alone is never Available. Initiation commits stable owner/operation/hash/size before transfer. Upload stores and verifies exact bytes before recording Uploaded. Finalisation re-verifies bytes and atomically records Available plus its receipt. A storage-success/database-failure retry reuses the original upload identity and immutable bytes. Missing bytes stay owned and recoverable; no deletion/cleanup is implemented. Supported PNG is a synthetic prototype boundary, not a claim of general phone-camera format support.

Completion drafts are versioned technician preparation, not API-C16/TR-11 submission. Exact entry IDs/versions and task outcomes, explicit personal time/material declarations, attachment states and remaining-work ownership persist. Missing required bytes and unresolved evidence appear as blockers; Complete cannot conceal safety/control failures or incomplete task outcomes. Saving any draft changes no reviewer/report/order/ticket/Finance closure. P09 will implement submission and reviewed entry sets; P08 will implement bounded offline recovery. No fake downstream records or approvals are introduced.

Current capability plus company/site/appointment/assignment/file scope applies before every read, write and original receipt recovery. Captures are owned by the server actor; another crew member cannot correct them. No generic attachment URL or arbitrary attribution is accepted. Screens keep the submitted operation and payload in memory for unchanged retry; no browser durable offline claim is made.

Alternatives considered: in-place edits destroy provenance; reusing acknowledgement as attendance invents work; a new object service or image dependency adds infrastructure before a demonstrated need; broad JPEG/HEIC support needs a separately pinned decoder and metadata policy. The bounded PNG decoder uses Node's built-in zlib and exact bytes. PostgreSQL exclusion constraints are documented in [PostgreSQL 16 range constraints](https://www.postgresql.org/docs/16/rangetypes.html#RANGETYPES-CONSTRAINT); the workflow and media limits are PPO synthetic policy decisions.
