# Service Cases & Triage workspace r01

**Owner:** Dean Fiedler · **Date:** 15 September 2026 · **State:** Requested standalone design delivered for review; native visual/device acceptance and application integration pending.

The [interactive HTML](../reference/ui/service-cases/PPO-Service-Cases-and-Triage-Workspace-r01.html) is the internal support front door requested by Dean: a Powerplants employee records a customer's issue; the Service Manager reviews its impact, selects a response and assigns an owned action; a technician or specialist records evidence; the manager reviews resolution and customer contact before closure. It uses the r20 theme with only the module's own header, context and local views. There is no left navigation rail, corporate masthead, customer login or external messaging action.

## Six connected views

1. **Case register:** six queue tiles for all cases, new intake, urgent open cases, waiting/information, overdue commitments and resolution review. Search and customer/site/case-owner/priority/category filters operate together. Filtered-out selection is cleared, and unavailable record actions are disabled. Mobile CSS presents register rows as labelled cards.
2. **Case workspace:** original symptoms, reported crop/production impact, temporary arrangements, customer/site/facility/equipment context, Google Maps address link, next actions, related-case candidates and history. Quick capture and captured-detail correction open as focused forms.
3. **Triage & actions:** reviewed priority, response route, case owner, escalation instruction, action assignment, outcomes and explicit transfer references/receiving owners. Waiting reasons cover customer information, parts, supplier advice, quotation approval and site access.
4. **Work & visits:** prepare a local Draft work order, link an existing work order for the same customer/site without duplicating its identity, propose a technician visit and inspect an exact preparation brief. These actions do not authorise work, reserve time or confirm attendance. Source work records retain their own scope and visits.
5. **Evidence & updates:** Reported symptom, Suspected cause, Attempted fix, Verified finding and Work completed remain typed and attributable. Original image attachments have exact context and source notes. Corrections append an observation retaining the original. Contact records distinguish Contacted, Message left and No response; an internal discussion cannot satisfy customer-contact closure requirements.
6. **Resolution & review:** open actions, waiting and unfinished/proposed work block resolution. A proposal identifies supporting current evidence. Manager return creates an owned action and preserves the proposal in history. Accepted resolution is retained separately from closure; closing requires successful non-internal customer contact after the resolution review. Reopening retains the case reference and earlier closed outcomes.

The main demonstration starts with an urgent intermittent fault involving the one Willowbank pump installed in Irrigation Shed 01 and serving Greenhouse 01, Tunnel 01 and Propagation House 01. An earlier closed case preserves an attempted restart and an unverified underlying cause. Other examples demonstrate unknown sensor identity, a completed diagnostic visit with outstanding parts, an invoice referral and remote support awaiting resolution review. A visit's completion never changes the case to Closed.

## Local behaviour and boundaries

Manager, Employee, Assigned technician and Observer are local preview roles. The technician preview is restricted to cases with its recorded involvement; it cannot export the full workspace, triage, assign case ownership or close cases. The observer can inspect but cannot mutate. These controls demonstrate the intended workflow; they are not authentication or server security. Real employee permissions, manager delegation and all related-record/file access must be enforced through existing domain services during implementation.

Expanded case states use the dictionary's existing New, NeedsInformation, Triaged, Active, Waiting, Resolved and Closed values. **Awaiting review** is the display of a separate resolution proposal, not a new canonical Ticket state. The current application still has its bounded P03 New/NeedsInformation/Triaged command contract. Organisation-level remote/departmental triage without a site is demonstrated here; it is a proposed extension to the current known-site runtime gate. On-site routing and work preparation in this design require a known site. This contribution does not silently lift a running-app guard.

Work-order links resolve to one retained source record. Draft scope and Proposed visits are intentionally held for receiving work-order/planner decisions. Full work approval, calendar capacity, confirmed assignment, dispatch, technician job packs and reports continue in their existing modules. This HTML does not simulate their completion by changing a case status. An outstanding action can be explicitly transferred with a receiving reference and responsible person; it cannot transfer back to the same case. Receiving-record existence/acceptance must be checked by the future integration.

Contextual assistance is scripted from the selected case, current evidence and actions. It offers a summary, missing-information prompts, technician brief and customer-update draft, with inspectable exact sources. Stale source data blocks use of a draft. It performs no model inference, technical diagnosis, email delivery, supplier contact or external handover. MYOB case mappings remain unconfigured; a future linked reference must retain company context and source evidence without replacing the existing PPO identity.

This is a single embedded file with no network-loaded fonts or assets. Google Maps opens only an explicitly selected fictional address through a standard address search link. The local key is `ppo-service-cases-triage-r01`. Validated JSON backup/restore, explicit reset, stale-write refusal and session-only storage failure messaging are included. The queue clock is visibly fixed at 15 September 2026, 10:00 AEST for repeatable examples; entered times use Australia/Melbourne and history retains recorded timestamps. No SLA response target, warranty decision or live urgency/dispatch authority is implied by a priority label.

Original JPG/PNG/WebP uploads are limited to 1 MiB each, twelve original files per workspace, dimensions up to 10,000 pixels and 6,000,000 JSON characters overall. File bytes are stored once and referenced by observations/history. Browser quotas may be smaller. Original metadata is not stripped. Upload decoding and file signatures are checked; restored-file structural checks are not cryptographic authenticity or controlled document storage. SharePoint remains the intended business-document authority and MYOB the ERP authority.
