# Accepted Won handover to native delivery

<!-- versioning: git; committed history is authoritative -->

Owner: Dean Fiedler. Date: 7 October 2026. Review: proposed implementation under the user-authorised Leads/Deals programme; owner acceptance pending. Scope: CRM-03 / CRM-08, CR-01, existing Won receiving, Project and Service work-order scopes. Contract: [lead-to-delivery continuity](../contracts/lead-to-delivery-continuity.md).

An accepted Won handover retains its exact Sales content and receiving decision. Its receiving owner explicitly creates a native Project or Service work order, or selects an existing permitted record, and then makes a separate link decision. Native creation retains its own command and original receipt. Linking never copies or approves scope, creates schedule tasks, authorises work, books appointments or completes the Sales Activity.

The native destination must belong to the same company and customer, have a current customer/site relationship, and be owned by the receiving actor with current native editing access. A known Sales site must match. When Sales retained an unknown site, the chosen native site is separately shown and explicitly reviewed with the link reason; the accepted Sales source is not rewritten. A closed Project cannot receive a new link. Service keeps its existing request, scope and authorisation controls; at least one native service request remains required to create a work order. Parts routing has no equivalent native receiving destination and remains an explicit unresolved route.

Migration 0076 adds an immutable companion keyed to the exact accepted handover event and typed native destination. Compare the current Sales version/source hash and the current destination version/site. The companion, audit, receipt and publication commit atomically. Existing Project records have no native Deal key, so the explicit companion is the relationship; free-text Project/Opportunity references in Service are not treated as typed authority. A destination can retain multiple explicitly reviewed Sales sources without merging their scopes or obligations.

Source or destination changes refuse new link intent. Native creation remains independently governed by its native authority. A later Sales successor leaves the earlier binding visible as historical. Actor-bound original recovery requires current access to the captured Sales and native target and the original receiving capability, without requiring the actor still to own that target or the current handover. A denied refresh removes the comparison; an uncertain command retains its exact original operation across reload. Create and link remain independently recoverable. Creation recovery is keyed to the exact Sales acceptance and native kind, so a later accepted successor can start its own deliberate creation. Service can save a request through the existing intake form and return with its exact native identity before saving a work order.

Deal progress reads the real handover and binding records, native destination state and existing Activity owners/dates. Accepted receiving, linked destination and completed native work are separate facts. The original Won handover-due event is retained, while the UI labels subsequent receiving progress from its actual sources. No percentage, inferred delivery completion or second lifecycle store is introduced.

The existing application stack, PostgreSQL transaction and native create/read commands are retained. No technology, dependency, capability, grant, seed or user is added. Issued references, ES-05 source hashes and historical Sales hash strings remain unchanged. Synthetic functional proof, paired design review, owner/business acceptance and deployment remain separate.
