## Authoritative facts and bounded semantics

Keep the pinned application stack, PostgreSQL workspace/operation transaction locks, shared controls, verified private byte adapter and immutable templates. A new workflow engine, customer portal, signing service, notification platform or report renderer would duplicate established contracts and is rejected.

`ppo.customer_responses` remains the authoritative captured response. Add an immutable companion in `ppo.customer_response_contexts` with subject `ReportContent` or `AttendanceFacts`, exact approved review, current capture binding/restriction observation and optional predecessor response plus correction reason. Legacy rows without a companion mean ReportContent; they are not rewritten. Migration 0057 is available after inspecting main, the live schema and migration registry; preserve 0051/0052 reservations and all installed seed/migration bytes. No new identity type, capability, grant, seed or template is required.

AttendanceFacts acknowledges only the named technician's original actual attendance and declared end/context as shown in that exact reviewed HTML. It does not accept technical work or all report content. This first bounded acknowledgement is available after authorised factual Service review, using its existing DraftEvidence or IssuedReport presentation; pre-review attendance signatures are unsupported. The original attendance, appointment, work order, company/site, exact equipment/scope, report revision, review, issued identity (where applicable), presentation kind and HTML hash remain relationally bound. Presentation/capture times are stated client facts subject to existing ordering bounds; receipt time and capturing actor are server facts. The named audience comes from the exact review; respondent name and role are explicitly stated and may describe that audience's representative, without independent identity verification.

Both subjects retain Accepted, AcceptedWithReservations, Declined, Unavailable and Disputed. No response is a separate visible state, never inferred acceptance. Non-Accepted requires a meaningful explanation and next action. Unavailable has no name, role or mark. Optional bounded synthetic PNG marks remain original protected evidence, not legal signature assurance. PDF retrieval never records a response. A draft response never transfers to an issued report, including an attendance acknowledgement.

New independent responses have independent UUIDs even when text looks similar. An explicit correction appends a successor to one response of the same report, subject and exact presentation, with a meaningful reason. Only one direct successor is permitted; competing corrections conflict. It may correct stated factual capture or clarify reservations without altering the original. A changed report uses the existing factual correction, successor submission/review/issue and a fresh response; it cannot inherit a prior mark or response. A correction neither completes nor deletes the prior obligation. Reuse its still-open Activity where permitted; if that obligation is closed, a new non-Accepted response creates a new owned obligation. Accepted corrections create no new obligation and do not silently close existing work.

## Authority, restrictions and exact recovery

Use current scoped `report.read` and `report.respond`; neither grants review/issue, Service edit or incident-sensitive authority. Review/issue retain their current-owner duties and existing attendance/appointment effects. Recheck current company/site/appointment/report scope for every read and command; the original actor's current response duty governs receipt recovery. Current recipient, customer/site/equipment identity, Service owner, assignment, scope/pack and evidence binding changes require a fresh reviewed presentation before a new capture. Missing/inaccessible required sources or original bytes are unavailable, never clear. Previously accepted receipts prove their original fact after current permission checks; later source changes do not rewrite them or imply present clearance.

A factual response to exact retained content may be recorded when an incident hold, inspection failure or other technical restriction already exists or arrives after presentation, provided the source/recipient/evidence binding still passes. Store and display the current restriction observation without incident titles, IDs, counts, restricted evidence or review notes. This permits documenting disagreement about retained facts; it does not permit starting work, releasing an inspection outcome or claiming clearance. Inspection correction, exact retest and independent acceptance, incident closure, readiness, assignment, competency and scheduling retain their own commands. Customer response never completes an appointment, order, ticket, project or Finance handoff, approves billing/statutory compliance or settles warranty.

Follow-up uses actual Activities/My Work: `activityCommand` update for owner/due changes and owner-only start/complete/cancel with exact versions and retained audit. Report links retain the originating response/review; summaries carry only customer-response facts, never incident details. Activity completion does not erase a reservation/dispute or alter inspection/incident authority. Return preparation uses `POST /service/work-orders/:id/visits` with current order version and exact approved scope. Proposed is not scheduler acceptance, confirmation, availability, work authority or a pack. Broader SV-06/SV-07 aggregation and orchestration remain outside FI-07.

Online states are unsaved, saving, saved, validation failure, stale/conflict and uncertain. Preserve editable rejected input and the immutable original operation/payload on uncertain results. The existing same-tab journal stores before sending, locks to actor/workspace and recovers receipts before another command. Explicit retry sends only the original. P08 retains exact cached HTML/hash, owner-bound originals, dependency adjudication and current server revalidation. Absent FI-07 extension fields preserve the original P09 normalised hash. Supported existing response/submission replay remains; no offline review, issue, incident commands or background sending is introduced. Historical files and marks remain exact under current file authority.
