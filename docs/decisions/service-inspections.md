## Contract

FI-03 (`/my-jobs/inspections`) and FI-04 (`/service/inspections`) consume the existing shared inspection engine. Engineering keeps its real ProjectCommissioningScope host and EN-08 contract. Service uses real appointments only. No second attempt, reading, evidence, review or defect engine is introduced.

Each attempt binds an immutable catalogue version, stable procedure identity, exact authorised scope item and Equipment identity, current equipment/configuration snapshot, appointment/schedule/assignment versions, personal attendance, issued pack and readiness sources. Catalogue records and fictional criteria are persisted and immutable; retirement is a separate retained event. No general template authoring or OEM limit authority is added. A new version never rewrites an old attempt. Check occurrence keys are hashes of the procedure identity, scope-item ID, equipment ID and stable template check key; names and template revision numbers are not identities.

Service drafts are partitioned by performer and exact procedure/equipment/scope/context binding. A technician may hold several procedures, and two assigned technicians may capture independently. Changing attempts with unsaved input requires explicit discard; supported record links retain the attempt ID. One performer cannot open two drafts for the same exact binding. Changed context permits a new bound draft while the old draft remains visible as requiring reassessment. No readings or evidence are copied into a retest. EN-08 retains one open draft per host. All writes use the existing workspace transaction lock, optimistic versions and original-operation receipt contract.

Capture requires current assigned `field.read.own` and `field.capture.own`; submission additionally requires `field.completion.own`. Actual attendance, current authorised scope/issued pack, dispatch/readiness and Scheduling Step 6 policy holds are rechecked on the server. A readable historical attempt is not capture authority. Draft evidence belongs to its performer. Review uses existing scoped `report.read` / `report.review` and release uses `report.issue`, with `service.work_order.edit` and the named Service owner, plus existing schedule/work-order/customer/site visibility. Reviewers receive no technician grants. Independent review is mandatory. Receipt disclosure rechecks the original command duty before returning accepted history; changed readiness prevents new actions but does not erase accepted receipts.

Submission freezes raw entries and computed evaluations together. Failed or incomplete required checks create/reuse the shared owned defect in the same transaction. A RestrictedService Activity is created through the existing owning-domain command primitives; an unavailable action is an explicit refusal, not a fictitious handover. Repeated failures retain the existing defect. Service closure requires a recorded correction, an explicitly linked successor containing that occurrence, a fresh passing result, current applicability and an independent accepted review. Completing the Activity cannot close the defect. The initial corrective owner and due date remain fixed: coordinated Activity/defect reassignment is unavailable in this increment, and the API refuses a silent divergence. Retest cannot be waived. System-changing work remains outside the inspection release and requires the owning Engineering process.

Calibration is assessed against the snapshot retained at capture and the test date. A later renewal cannot validate historical use. A retrospective withdrawal still withdraws current applicability. Missing criteria, unknown conditions and unknown calibration do not become verified passes. Supported media remain verified PNG and bounded plain text using the existing exact-byte document store; all other media remain unsupported.

Release is an internal, narrowly scoped inspection outcome for the selected accepted attempt and its procedure/equipment/scope. It retains original attempts, failures, correction/retest and review identities, exact hashes, exclusions and outstanding work. It rechecks current source/configuration/readiness and blockers. The existing controlled bundle renderer/store produces retained HTML/PDF bytes; reopening checks audience, source bindings and byte hashes, and displays current applicability separately from issued content. Release completes no appointment, work order, Project, customer acceptance or Finance process. FI-06 incident clearance has no authoritative source and is explicitly unavailable. No unavailable receiving workflow is simulated.

## Online recovery and alternatives

This increment is online. Durable server drafts survive reload and restart. Unsaved edits are browser memory only. An uncertain operation retains its unchanged ID and payload for original recovery; identity changes cannot disclose another person's original. No new offline inspection queue is introduced. Existing P08 commands remain unchanged. Disconnected capture must say what was last saved and refuse any claim that unsent edits are persisted.

Reuse Next.js/React, PostgreSQL, current shared controls, operations and document storage. A separate engine, host-wide multi-user shared draft, guessed Engineering appointments, broad reviewer technician access, generic workflow service and live template/OEM integrations were rejected because they would weaken ownership, provenance or scope. Additive migration 0055 is allocated after 0054; 0051/0052 remain reserved. Installed SQL/seed bytes and retained-root repair remain unchanged. No new capability or grant is needed.
