## Context

BP-04 / BC-04 / ES-04 already has immutable complete releases, schema 3 rule members, schema 4 Cost Sources, exact rebase and release-quality assessment. These do not provide independently owned packages. The next P1 boundary in the CPQ backend plan is package versioning, fixture responsibility and measured representative workloads. CREMS reconstruction, new price books, UI and deployment are outside this decision.

## Decision

Use the existing PostgreSQL database, native UUIDs, shared atomic operations and CPQ company permissions. Migration 0102 adds a `CpqPackage` identity, package roots, immutable revisions and events, and a closed release-to-package manifest. It adds no grant, seed, library, service or calculation schema. Schemas 1–4, definition hashes and existing persisted evidence keep their original meanings. Package workflow and manifest schema 1 are separate contracts.

A package has one immutable company, kind (`Rules` or `Tables`) and owner (its creating actor). Only that owner, with current `cpq.author`, can revise or withdraw it. Ownership is responsibility, never an access grant. Ownership transfer is a separate future policy. Revisions contain a normalized existing CPQ definition as a rehearsal context, selected member keys, a native fixture-owner user ID and declared synthetic workload targets. Tables use the actual schema 3 decision-table model; this increment does not combine schemas 3 and 4. Member identity is the exact native package revision plus its unique authored member key; labels are not identities. An unchanged member in a later package revision remains distinguishable through its content hash; a separate member registry is unnecessary for this bounded increment.

The fixture owner must explicitly attest the exact revision after running all its fixtures and bounded workload measurements. A separate current `cpq.review` actor reviews that stored evidence. A separate current `cpq.publish` actor publishes the exact revision. Authors, fixture owners and reviewers cannot publish their own evidence. Revise, failed attestation, review, publication and withdrawal retain immutable events, audit, receipts and outbox evidence. Current source and actor authority is rechecked at each new-use boundary. Original-operation recovery reauthorises the original retained sources without demanding that they remain currently published.

Package workload targets identify a synthetic family and rationale, maximum evaluation milliseconds and maximum serialized result bytes. All fixtures are measured three times inside the existing isolated worker, within its unchanged five-second and memory limits. Store each sample, maximum, input/output sizes, case dimensions, runtime version and scope with the exact target/fixture hash. This is in-worker evaluation time, not API latency or startup performance. A failed target or fixture is retained as failed evidence and cannot be approved. At most six workload fixtures are accepted per package. Small, typical and boundary fixtures must be supplied and explicitly labelled by the owner; no real operating family, percentile SLA or capacity commitment is inferred. Operational targets require later representative business data and acceptance.

Release save accepts an optional exact package manifest outside the calculation definition. Every rule (and every schema 3 decision table) in a package-governed release must be supplied exactly once by published package members; missing, overlapping, changed or extra members refuse. Compatible rehearsal contexts share schema, facts, constraints, technical part shapes and non-table design contracts. Prices remain authored under existing contracts, including exact Cost Sources; candidate fixtures from every package are rerun against the complete candidate definition so a changed cost or context cannot silently invalidate the package evidence. Release roots cannot drop package governance after enrollment. No command selects a latest revision implicitly.

Manifest insertion closes with creation of the immutable release revision. It records exact package revision, content hash, publication event, owner, fixture owner and evidence hash; later insertion or mutation refuses. Package-governed release activation additionally requires the existing independent release-quality assessment. Calculation and rebase freeze the manifest in optional binding evidence; adoption rechecks current exact publication and authority and retains it through the saved run and receiving audit. Historical runs, estimates and original receipts remain readable under current authority after withdrawal. Customer quotation projections do not include package owners, fixture data, targets or internal provenance.

## Alternatives and consequences

Reusing release roots as packages would conflate independent ownership and complete release publication. Storing package state only in release audit would leave no independent native identity or database-enforced closure. A separate service or generic package registry would add unnecessary infrastructure. New calculation schema 5 would unnecessarily change the runtime and historical hashes. The selected relational extension keeps these concerns explicit and enforces history with the existing immutable-evidence and deferred-operation idioms.

Full rehearsal definitions intentionally favour a reviewable bounded contract over a new interface/DSL. They can repeat context, and price changes that alter expected fixture results require an explicit new fixture/package revision. This is not a new pricing authority. Limits remain conservative; workload results are machine observations, not business acceptance. Future ownership transfer, multi-package dependency graphs, cross-schema composition and operating service objectives need separate decisions.

## Verification and handover

Independent review of PR #498 identified that database-side manifest insertion checked exact member bodies but not the stored member hash projection. Close that gap inside the still-unmerged 0102 migration with a narrow native PostgreSQL serializer for rule/table members: ordinal ASCII field ordering, semantic array order, JSON strings/booleans/null and safe integer priorities. Numeric rule quantities and condition values already use strings; unsupported numeric shapes refuse instead of guessing JavaScript float formatting. Compare the entire stored package snapshot with the native projection, including ordered member hashes. A generic JSON canonicalization library or an additional canonical-byte store would add a new dependency or duplicate persistence unnecessarily. Preserve the original local database snapshot and evidence before resetting the disposable test database; rerun populated 0101 upgrade and repeat stability against the amended migration. No applied shared/hosted migration is rewritten.

Prove publication independence, fixture-owner acknowledgement, exact coverage and compatibility, existing Cost Source authority, tenant isolation, stale/withdrawn refusal, immutable history, concurrent/repeated operations, rollback, original receipt recovery, quotation privacy and actual restart recovery. Follow every migration-registry and populated historical-upgrade obligation in AGENTS.md, preserving original ledgers, grants and rows. Record local checks, exact-head CI, independent automated review and operational acceptance separately. Update API, delivery plan, STATUS and execution evidence. Do not merge or deploy.
