# ADR-0021 — Gmail as the first real mail provider, on the hosted-only schema track

**Date:** 11 September 2026 · **State:** schema and operator scripts authorised by Dean. No Google project, client, secret, route, sync code or deployment is created by this decision.

Dean authorised a read-only Gmail connection for the hosted private demo, importing only the messages he has individually labelled in his own mailbox. This is the first path in PPO that can carry real correspondence. [ADR-0020](ADR-0020-email-calendar-synthetic-journey.md) and the [integration design](../blueprints/email-calendar-integration.md) assumed Microsoft Graph and synthetic content. That design's provider-neutral types are retained; Gmail is added as a second provider and does not replace Graph as the later intended interface, and no Microsoft work is superseded.

**Real content does not enter `ppo.email_messages`.** Migration 0015 constrains that table to `provider='Synthetic'`, `synthetic`, and `sender_address LIKE '%.example'`, and requires a `company_id` that an arbitrary inbound sender does not have. Those constraints are the guard that keeps the rest of the demo synthetic, and relaxing them would remove it for every existing row and screen, not only for Gmail. Gmail therefore gets its own tables — `mail_connections`, `provider_messages`, `mail_message_links`, `mail_sync_checkpoints` and `mail_connect_attempts` — implementing the MailConnection, ProviderMessage, CommunicationLink and SyncCheckpoint types the integration design already named with no migration allocated. `ppo.email_messages` is unchanged and keeps the synthetic fixture journey. Company context enters only at link time, from the chosen opportunity, so an unattributed message needs no sentinel company.

**The schema goes on the hosted-only demo track, not the local migrations.** `db/demo/0001-identity.sql` states that track's purpose: real identity exists only where the hosted environment does. `localConfig()` structurally refuses anything but loopback with synthetic identity, so a Gmail connection cannot be exercised locally; a local migration would add unreachable tables, change the issued local checksums and collide with migration 0020, already proposed by PR #108. `db/demo/0002-gmail-connection.sql` leaves the issued local track untouched. `migrateDemo()` and the existing-demo upgrade are generalised from the single hardcoded identity file to an ordered demo registry, preserving the recorded version-1 checksum and its legacy CRLF encoding.

**Ownership binds to the Google account identifier, not the address.** The integration design requires that reconnection must not reassign ownership from a changed email alias, so the connection anchors to the permanent OpenID subject and `openid` and `email` are requested alongside `gmail.readonly`. That also reuses the existing `openid-client` dependency and the `demo-auth.ts` PKCE, state and nonce pattern rather than adding a second hand-rolled token exchange. Google issues a refresh token only when the authorisation request sets `access_type=offline` and `prompt=consent`; there is no `offline_access` scope equivalent. `gmail.readonly` is a Google restricted scope: acceptable while the project's publishing status is Testing, and subject to a security assessment before any verified application. Label selection uses the immutable `Label_*` identifier, not the display name, so renaming the label in Gmail cannot silently empty the import.

**Cached provider content is deletable; PPO evidence is not.** Every other table in this schema is append-only under `immutable_evidence()`. Provider messages are a cache of a mailbox PPO does not own, and must be removable on disconnect and on an explicit purge, so they carry no append-only trigger and cascade from their connection. Audit events recording connect, disconnect and purge remain permanent. The database also enforces that a `Disconnected` connection holds no token bytes, that stored token material is a complete AES-256-GCM triple of the correct lengths, and that `error_code` matches a code pattern so a provider failure cannot carry a subject, address or body fragment into stored state.

Alternatives: relaxing 0015's checks is fewer files but removes the synthetic guard across the whole email surface and forces a sentinel company for unattributed mail; a local migration puts the tables in the only environment that cannot exercise them and collides with a reserved version; the `googleapis` package adds a large dependency for requests `fetch` makes directly; Azure Key Vault instead of encrypted columns adds a service to the demo without changing who can read the tokens.

Not decided here: more than one selected label, HTML body rendering and sanitisation, attachments, calendar, sharing a message with another tester, and whether a Gmail-linked message may create an Activity. This decision authorises no Google configuration and no connection.
