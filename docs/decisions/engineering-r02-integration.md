# Engineering r02 — accepted design and first implementation

Dean accepted Engineering r02 on 10 September 2026 and authorised moving into implementation. The exact [HTML](../reference/engineering-r02/PPO-Engineering-Container-r02.html) and [audit](../reference/engineering-r02/PPO-Engineering-Audit-r02.md) are retained unchanged. The design uses Roboto, navy/green, outer gutters, a resizable register and the Overview / Deliverables / Technical queries / Review & history drawer.

The first implementation covers ENG-01 and the owned-context/note part of ENG-02/ENG-04: persisted engineering requests linked to an existing permitted Project or Opportunity, a currently eligible engineer, discipline, brief, separate package/action dates, and attributable notes and coordination history. Queued, In design and Awaiting information are coordination states. They do not approve effort, certify a design or authorise document issue. The assigned engineer owns the next action in this increment.

Reuse the existing Next.js/React, PostgreSQL, scoped permissions and original-operation receipts. Additive migration 0020 introduces typed packages/events and engineering.read/create/edit capabilities. Applied migrations 0018 and 0019 remain unchanged. Synthetic coordinator scopes receive these grants; no Systems or broad workspace access is inferred. Real technical competence/issuer authority remains unresolved.

The approved review/released tabs and drawer structure remain; no fabricated documents, checks, technical queries, reviewer assignments or issue histories are seeded. Those areas explicitly describe their current empty state. Presales links use Opportunities; project links indicate project work and do not imply a signed customer order. Service-specific links, document metadata/CAD previews, technical query commands, review snapshots, approval and issue authority are subsequent increments. No live SharePoint, SOLIDWORKS, customer notification or ERP operation is introduced.

Requests have immutable source relationships and optimistic record versions. Permission and source-context checks precede reads, mutations and operation replay. Each accepted change stores an immutable event, exact package snapshot, audit, outbox entry and receipt in one transaction. Duplicate original commands replay; changed originals conflict. No operational records or pending commands are placed in browser persistent storage. Unsaved request/note fields remain while navigating the module; leaving/reloading warns of unsaved or uncertain work. Identity changes clear the page through the existing session boundary.

The broader [master Engineering scope](../blueprints/BP-01-master-blueprint.md#11-engineering-and-design-control-capability-blueprint), ENG-01–ENG-07, D-008/D-019 and AT-15/AT-37 remain intact. User confirmation establishes the authoring environment as SOLIDWORKS and the current file location as SharePoint; versions, model dependencies, PDM arrangements and supported integration remain to be verified. Follow-up is tracked under [PPO-011](https://github.com/deanrfiedler-gif/powerplants-one/issues/11).

Implementation and test evidence is recorded in the [handover](../delivery/engineering-intake-handover.md). Design acceptance does not establish merge, deployment or operational acceptance.

Dean subsequently explicitly authorised publishing the implementation branch and opening a draft pull request in his public Powerplants One repository, resolving the initial automatic publication hold. Main reconciliation and verification are recorded in the handover; merge and hosted rollout remain separate.
