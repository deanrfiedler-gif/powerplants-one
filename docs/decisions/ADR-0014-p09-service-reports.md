# ADR-0014 — P09 exact completion, service review and customer reports

**Date:** 6 September 2026 · **Status:** Implementation in progress, verification outstanding · **Authority:** [P09 issue #36](https://github.com/deanrfiedler-gif/powerplants-one/issues/36). Synthetic only.

Retain the pinned monolith, PostgreSQL workspace/operation transaction locks, immutable original evidence and existing private write-once byte adapter. No new dependency or service is required. API-C16 submits completion; API-C17 reviews/returns; API-C18 issues and records responses. API-C19 remains P10.

Each actual attendance has one report aggregate with immutable submission/content revisions. It belongs to one appointment and one original technician. Multiple actual attendances can produce separate attributable reports; no technician submits another person's declarations. First submission moves InProgress to CompletedPendingReview and prevents additional physical starts. Each already-started technician submits independently. Acceptance records an immutable attendance acceptance; the appointment becomes Completed only after every actual attendance is accepted. Unstarted assignments do not become attendance. Submission declares the actual attendance end explicitly. Return retains CompletedPendingReview. Accepted attendance is never reopened by a report correction; further physical work needs a separately authorised proposed/confirmed visit. Order/ticket/Finance closure is unchanged.

Submission references a saved exact completion draft, its entire current own entry set, original attendance/scope/issue, exact attachment availability/hashes and declarations. Incomplete declarations, missing bytes, changed draft/evidence and restricted recovery prevent submission. Partial/UnableToProceed preserve unresolved controls and an owned next action. Evidence capture freezes while Submitted. Return allows only linked factual corrections, without a new start. After accepted review a technician explicitly opens a correction cycle; only successor factual corrections are permitted, retaining attendance and prior report history. Originals never change; corrections invalidate current report eligibility.

Service review belongs to the current scoped service owner with explicit review capability. It records decisions on every exact entry, immutable return comments and technical quantity acceptance, separately from any future financial treatment. Changed scope/pack requires an explicit original-attendance-only disposition and reason; it cannot waive a mandatory control or make unfinished scope Complete. Customer content uses an allowlisted projection of exact evidence with attribution/confidence; staff time notes, stock/provider references, internal review notes and attachment filenames are excluded. A named active site contact is explicitly selected before review. A previously submitted Complete outcome can survive a returned or accepted report correction when the original scope/pack remains applicable and every current declaration/task/byte/control check still passes. This is factual completion review, not renewed physical-start authority.

Every material report correction uses a successor review/issue/response cycle. Rendering reserves an output preparation time and issue UUID; actual release time is a later immutable fact. An owned durable attempt stores one exact HTML/PDF bundle, validates it, then rechecks review/source/template/recipient/current permissions before final issue. Recovery locates original bytes; it never regenerates a stored old issue. DraftEvidence presentation is a retained, explicitly labelled exact snapshot and can never be promoted to IssuedReport.

The bounded presentation format is HTML. IssuedReport binds the hash of the HTML from the exact released bundle; the separately immutable PDF hash remains on its issue manifest. Opening the PDF is not a response capture. Offline HTML bytes must match the presented hash before local persistence.

Responses retain exact report revision, presentation kind/content hash, stated respondent identity/role, presentation/capture/server times and capturing actor. Reservations, Declined, Unavailable and Disputed require meaningful explanation and owned next action. Unavailable has no invented respondent or signature. Optional bounded synthetic PNG marks are write-once protected response evidence, bound to the complete original response operation; no existing response/signature reassociation parameter exists, and a mark already bound to different content on the same report is refused even if its bytes are uploaded again. No response signifies independently verified identity, billing approval, whole-project acceptance, statutory compliance or warranty settlement.

P08 schema-1 originals remain compatible. New explicit submission/response commands use the existing owner-bound queue, dependency adjudication and receipts; no offline approval/issue or background sender. Cached exact presentations remain stale context. Current permission and exact presented content govern server acceptance; unknown responses recover their original receipt. Restricted recovery is not extended into normal report/file access.

Operational branding/wording remains D-024; SharePoint/MYOB configuration, device security/retention, owner acceptance, independent review and production readiness are not resolved by synthetic implementation. Primary technical references checked 6 September 2026: [PostgreSQL 16 locking](https://www.postgresql.org/docs/16/explicit-locking.html), [Playwright PDF API](https://playwright.dev/docs/api/class-page#page-pdf), [IndexedDB transaction lifecycle](https://www.w3.org/TR/IndexedDB-3/). Workflow policy above is a bounded PPO implementation choice.

Offline submission preparation requires a downloaded accepted attendance/version; pending P08 starts and their captures synchronise first. New P09 intents may use a newer downloaded draft but never rewrite an existing queued payload. Conflicted originals remain retained and cannot enter restricted evidence recovery. The public recovery result exposes state and output availability, with private adapter identities retained only in server storage.

Partial/UnableToProceed submission and review preserve explicit Incomplete time/material declarations, reasons, blockers and owned next action. They may accept the factual attendance while retaining the incomplete record; missing quantities are never invented and Finance readiness is not inferred. Complete remains blocked by incomplete declarations. Required pending/missing-byte evidence still blocks every normal submission. This reconciles the maintained P09 requirement to review incomplete declarations with the physical P07 draft values.

The OUT-10 template definition fingerprints the actual report renderer/projection and shared rendering/escaping source bytes. Seed 9 stores that exact definition/hash and current policy in the same seed transaction; repeat seed never rewrites it. Issue request and final release reread and compare those source fingerprints. A changed template source, even during rendering, retains a StaleSource attempt without release. Future rendering changes require an immutable successor template/policy through an authorised forward change; old issued bytes remain retrievable without regeneration.
