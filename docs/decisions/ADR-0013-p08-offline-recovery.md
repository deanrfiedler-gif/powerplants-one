# ADR-0013 — P08 durable offline evidence and restricted recovery

**Date:** 6 September 2026 · **Status:** Implemented for the synthetic prototype; verification/publication in P08 handover · **Authority:** P08 issue #34. Synthetic local prototype only.

Retain exact dependencies and P07 domain commands. A small TypeScript-generated static field shell at `/offline/` has a service worker scoped to that directory. Its cache contains only an explicit versioned shell allowlist, never API responses, Finance pages, issued files or personal data. IndexedDB separates permitted context (at most two explicit jobs, 24-hour simulated freshness), original immutable operation envelopes, local evidence/PNG bytes and mutable sending/receipt/lease metadata. Offline start and acknowledgement remain intents. P09 response/submission/report and P10 Finance are absent.

The browser commits strict IndexedDB transactions before claiming local save. Original operation ID, schema, actor/workspace, exact issued/scope/assignment hashes/versions, dependency IDs, lineage and unmodified payload survive retries. Receipt persistence is a separate local transaction. Failed local saves retain unsaved form state; unavailable/blocked/version-change/abort/quota errors are explicit. There is no memory fallback, automatic deletion or background sender. Expired claims can be reclaimed; server receipts remain the final duplicate-effect protection.

API-C15 accepts at most 20 operations and 6 MiB, resolves immutable causal references, topologically orders siblings with stable input-order ties and isolates failures. A request-local AsyncLocalStorage hook records the original envelope atomically with the existing domain/audit/receipt/outbox transaction, under the existing operation/workspace locks. It does not replace current domain authorisation. Dependencies refer to same-actor/same-appointment accepted operations; required photo availability remains explicit. Resolving a declared attendance dependency is not rewriting original queued content. Changed accepted envelope reuse conflicts even if its resolved domain command would be identical.

Previously downloaded context carries a random, server-recorded recovery capability bound to the original active actor, exact authority and one appointment, expiring after seven days (synthetic test policy). Normal revocation never yields normal record/file/receipt access. Explicit recovery may preserve the original bounded evidence and exact PNG into a restricted case and owned Activity. Inactive identity, expired session, absent/expired capability or mismatched context retains evidence locally. Original actors recover only their own minimal case ID, original operation/hash, receipt/time and disposition; service owners need current existing scoped work-order-edit and Activity permissions and exact case ownership to inspect original evidence or bytes. No general revoked-user browsing or promotion into normal field evidence exists.

Identity selection/sign-out locks cached views before changing session and broadcasts the lock to tabs; unsent evidence remains assigned to its original actor. Reopening an offline browser can resume only the last validated owner until expiry; switching requires server identity verification. Storage markers detect partial eviction but cannot recover data the browser/user erased. This is a browser prototype, not operational device encryption/security or physical-disk durability certification.

Alternatives: caching full Next business pages risks broad dynamic response capture; a third-party offline framework adds dependency/version ownership without need; mutable rebasing destroys authority evidence; automatic retry after unknown outcomes risks duplicates; recovery through normal field APIs widens revoked access. The dedicated shell and narrow recovery preserve the existing boundaries with native browser APIs.

Primary references checked 6 September 2026: [IndexedDB transaction lifecycle and completion](https://www.w3.org/TR/IndexedDB-3/), [Service Worker scope/cache lifecycle](https://w3c.github.io/ServiceWorker/), [Playwright persistent browser profiles](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-persistent-context), [Node asynchronous context](https://nodejs.org/api/async_context.html). Browser restart tests establish only the executed Chromium profile behaviour. Operational devices/retention/identity remain D-016/D-020.
