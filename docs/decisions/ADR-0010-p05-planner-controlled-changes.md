# ADR-0010 — P05 planner and controlled changes

**Date:** 5 September 2026 · **Status:** Selected for authorised P05; verification pending.
**Related:** [issue #28](https://github.com/deanrfiedler-gif/powerplants-one/issues/28), SC-07/08, DAT-06, TR-03/08/16, API-R04/C04–07, EVT-02/03, SR-05/06/07/19/20, PT-08/09/10/26 components.

Extend the existing TypeScript/Next.js/PostgreSQL services and pinned dependencies. Retain the workspace graph transaction lock and acquire the union of old/new resource row locks in UUID order. Real half-open PostgreSQL exclusion constraints enforce reservation conflicts independently of application versions. Every crew replacement, appointment revision, consequence, audit, original receipt and outbox event commits atomically. No optimistic UI position becomes a saved booking until the server accepts it.

P04 appointments gain controlled current state while immutable proposal and per-version snapshots retain their original bytes and provenance. Scope and policy references remain fixed: stale proposals and unresolved successor drafts require a new proposal, not an implicit authority transfer. Booking approval records exact scope hash, versions, reviewed competency evidence, calendar and preparation evidence. Dispatch remains held: P06 pack preparation/review is represented as a typed requirement, with no invented pack or acknowledgement.

Fictional technician source bundles have explicit site eligibility, base timezone, effective dates, published weekly calendar/exception intervals, skill evidence and availability blocks. Published bundles are immutable, including child insertion; P05 exposes no resource, roster, skill, leave or policy editor. A later source-update command must use the same locks and booking impact evaluation before publication. This bounded alternative prevents a second mutation path from silently invalidating bookings. It avoids inventing operational rostering/overtime/trade rules. Every selected crew member must hold every scope-required synthetic competency through visit end; one Lead is required. Every travel allowance is explicitly supplied with a reason; zero requires an explicit decision. Calendar containment includes travel. No travel speed is inferred.

The predefined synthetic scheduling policy requires an evidenced manual/simulated customer date agreement before initial confirmation. A confirmed move may reserve replacement capacity with customer commitment Changed, an owned contact task and dispatch hold; a fresh contact outcome must explicitly record any later date agreement. Failed/no-response attempts do not imply commitment, sending, delivery or pack acknowledgement. Contact recipients are typed current site contacts within company scope. Scheduling consequences use typed appointment-to-Activity junctions and existing Site ActivityLink support; no generic future Report/Handoff targets are enabled.

Manual/ProjectReference requests require current request capability and appointment scope. TechnicianRequest additionally requires a current resource assignment for the server-derived actor; technician request authority never grants confirmation. Pending requests reserve nothing; acceptance reruns the full booking command in the request decision transaction. Decisions and cancellation retain explicit reasons and receipts. Cancellation requires future unstarted attendance and checks actual-work markers; P07 actual capture is absent and only component fixtures challenge refusal. No financial or document effects are erased.

All original migration/seed bytes, source baselines, parent requirement IDs, grants/revocations, counters and receipts remain intact. New seed receipt 5 is non-destructive. Technical sources checked: [PostgreSQL ranges](https://www.postgresql.org/docs/16/rangetypes.html), [locking](https://www.postgresql.org/docs/16/explicit-locking.html), [Next.js data security](https://nextjs.org/docs/app/guides/data-security). Synthetic policy is a project decision, not operational approval. P06+ and PP-01 acceptance remain incomplete.
