The written [PT-01 procedure](../testing/prototype-acceptance.md#pt-01--server-permissions-and-information-isolation) and BP-01 section 21.4 govern the expected outcomes. An explicit matrix covers Coordinator, assigned Technician, the four Finance duties, Systems without business grants, company-B and other-workspace identities, and site/workspace observers. Permission outcomes are specified independently of the runtime permission evaluator. Exact issued and generated HTML/PDF, manifests, draft/exact previews, field PNGs and captured synthetic response marks are included. Search, private notification state, counts, bounded windows, current grants and working-company narrowing use real HTTP adapters and a separate disposable PostgreSQL database.

The matrix reproduces four storage-time permission failures on unchanged main: field-photo bytes, field-photo metadata, and response-mark PNGs read as Technician or Coordinator still return HTTP 200 after their relevant grant expires inside the storage read. Reuse `attachmentContext` after photo verification and `reportContext` after response-mark verification, immediately before returning protected data. The metadata check belongs outside its recoverable storage-error catch so a permission refusal cannot turn into a metadata response. Original bytes, identities and hashes are retained; restored authority retrieves those originals.

This extends the existing authority pattern without a new service, dependency, migration, seed, capability or permission policy. Keeping only the initial check leaves the reproduced gap; holding locks throughout storage would introduce unnecessary contention. These are request-time checks, not a claim that a permission change can recall bytes already sent to a client.
