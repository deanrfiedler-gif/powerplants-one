# Naming, Communications and SharePoint — scope and design decision

## Authority and outcome

Dean requested the complete quoted design package: next naming-standard revision; functional specification; SharePoint architecture/configuration; interactive synthetic HTML; staged pilot/acceptance plan; and linked contract/register updates. The instruction follows this session's discussions of filename suggestions, legacy-name review, email/task conventions and a dedicated SharePoint area.

This adopts the shared capability as prototype design scope and authorises the documentation/prototype work. Detailed corporate configuration remains proposed; generated visual design has not yet been accepted. No real SharePoint provisioning, access change, migration, email, task notification, paid service or deployment is authorised by this package.

## Selected approach and alternatives

1. Extend PPO-STD-001 to r04; preserve exact accepted r02 and all issued baselines. Fixed rules establish formats; confirmed business records supply identities/revisions. AI description assistance remains a later bounded option.
2. Use one shared naming/filing/communication capability with channel-specific formats. A separate convention per business module would fragment references and duplicate work.
3. Suggest names for human uploads and legacy records; automatically name approved PPO-generated outputs and task notification drafts from actual records. Unattended retrospective renaming would create dependency and provenance risks.
4. Preserve original incoming/historical subjects and reply subjects by default. PPO-origin sending and Outlook-native compose assistance are separate increments. Provider identity and explicit record links remain independent of subjects.
5. Propose an isolated Sandbox site with three initial libraries, and a six-library operational information architecture with restricted commercial boundaries. A single catch-all library would mix audiences and lifecycle controls; a deep module/customer/site folder tree would overfit navigation and duplicate cross-domain documents.
6. Retain SharePoint business-file authority, PostgreSQL business workflows, Outlook message originals, native CAD dependencies and GitHub development sources. Existing files are linked/inventoried before any controlled migration.

No new framework, service or database technology is selected. Existing Next.js/TypeScript/PostgreSQL services and replaceable adapters remain the receiving architecture. D-003 stays resolved for prototype naming. D-012/D-024/D-025 and relevant Engineering/provider decisions remain open for operational evidence.
