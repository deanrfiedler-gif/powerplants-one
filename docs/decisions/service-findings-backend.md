## Closure and incomplete source contracts

The accepted design's examples are not executable authority where the native source has no corresponding transition. Inspection closure comes only from the native accepted retest; incident closure comes only from its independent source decision. Scheduling follows its native Activity outcome. Completing an Activity is shown separately from closing a defect, incident, incomplete report or customer reservation. Cancelled Activities remain visible as requiring disposition.

Report revisions and customer responses are immutable observations. A successor supersedes the earlier observation without deleting it or completing its Activity. The current services contain no generic `close finding` command for report remaining work or customer reservations. Those rows therefore remain open after follow-up completion and explicitly identify Service disposition or response correction as the owning workflow. This increment does not invent a rule that a reissued report, a later visit or an unrelated Accepted response clears them.

## R2 storage and command decision — 20 October 2026

Dean authorised the next backend increment after R1 merged. Reuse PostgreSQL, the native Activity writer and operation receipts. Instruction is the Activity summary, so My Work and Findings cannot carry different instructions. Required evidence is an Activity extension, keyed by its existing identity. A separate immutable source binding supplies a link only where a native source has no Activity; an existing native link always wins and a conflicting binding fails closed. These two small tables avoid rewriting immutable report snapshots or adding columns to every historical Activity snapshot. Encoding requirements in summary prose or reconstructing current state from audit history was rejected: neither provides a stable explicit field. No technology, dependency, capability, seed or grant is introduced.

Set/change requires current native source visibility, scoped `service.work_order.edit` and `activity.edit`. The proposed owner must currently read the source and be eligible to own the retained Activity and all its links. Technicians without Service edit remain view-only. A source token binds the native versions/state and exact source identity; the Activity version is checked separately. Assignment, instruction, evidence, history, receipt and outbox commit together. Exact retries recover the original result after later edits, provided the actor retains authority; a changed payload never reuses the original operation ID.

Generic Activity updates must not bypass source authority. Any R2 binding redirects new assignment/instruction/due edits to the R2 endpoint and exposes `can_edit: false` in My Work. Existing native tasks without an R2 binding retain coordinator editing: check scoped Service edit access, every linked native source for actor and proposed owner, and normal Activity owner eligibility. Classify native membership before permission filtering so an inaccessible source denies rather than falls through. This preserves the customer-response correction workflow, where the original Activity remains editable after its observation is superseded. Legacy edits retain Activity-version checks, not R2 source-token or source-state semantics. Guards run after original-receipt recovery; pre-0111 schemas and native owner start/complete/cancel keep their existing behaviour.

Closed or superseded sources and completed/cancelled Activities refuse a new change. R2 does not reopen, replace or complete tasks, accept evidence, close sources, change native defect/action ownership, remove incident holds, or issue customer messages. Those remain native workflows. Due time is an explicit UTC instant displayed in the site's timezone; it is required for a new save, and existing Activity appointment duration constraints still apply. Required evidence is explicit text or null when none is requested, not proof that evidence has been supplied.

PJ-06 competence/downstream disposition, PJ-07's controlling design-source discrepancy, PJ-08 update records, Warranty-to-Supply receiving and capacity/reservation rules remain BC-06 work. PJ-08's newer accepted design is preserved. None of these depends on duplicating T2b. Execution and exact failures belong in [evidence](../testing/evidence/service-findings/README.md).
