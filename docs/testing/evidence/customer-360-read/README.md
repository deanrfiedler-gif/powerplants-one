## Design and equivalence

`src/shared/customer-360.ts` retains the candidate queries, first-100 windows, source gates, source-error projections and DTO assembly. Independent sections, candidates and per-estimate quote lists share lookup waves through `src/activities/page-reads.ts`. Every reader drains before the original section, item and error order is restored. The native estimate, quote, Project, work-order and Finance readers still decide what is visible. Customer 360 now requests 50-parameter-set statements after the review's longest-statement check; Activities keeps the default 100. The adapter separates rows returned to duplicate consumers so native estimate annotations cannot affect another quote’s historical version.

`src/platform/permissions.ts` reuses only its exact existing permission query within the page. Parameters include workspace, actor, capability, company and Site. Every other SELECT still runs; the final organisation read uses the raw client. `src/shared/reads.ts` and `src/finance/accounts.ts` only add an optional internal query client; existing callers retain the original path.

`tests/helpers/customer-360-per-row.ts` is main’s unoptimised workspace function with import paths and its exported function name adjusted. Its body remains byte-equivalent to the original after those two transformations; current main’s reader is also unchanged. [Contribution accounting](contribution.json) retains the source hash and merge evidence.

The Activities detail-read comparison is **not independent**: the oracle's `listActivities` call also reaches this PR's changed `activityPageReads` through `src/activities/activities.ts:863`. That caller keeps the default 100-entry batch. Pages are capped at `rows.slice(0, pg.limit)`, at most 100 distinct values, so chunking never splits an Activities page. Row copies are shallow and carry identical values. `tests/unit/activity-page-reads.test.ts` is unchanged and passes; these facts support unchanged Activities output separately from the shared-adapter equality comparison.

`tests/database/customer-360-reads.test.ts` compares the complete DTO by deep equality and `JSON.stringify` equality with a fixed observation clock. Four principals cover broad access, one-site access, expired quotation/Project access and another company. The proof also checks revoked grants, a selected working company, the original 403/404 refusals and mixed visible/hidden deals, estimates, quotations, Projects, work orders and Activities. A second test creates 101 candidate chains and 100 additional revisions of the first estimate: the result retains 100 deals, 100 Projects, 100 estimates, 199 quotations and 100 Activities with the exact original continuation. The signed cursor itself is included in the unmodified JSON comparison.

`tests/helpers/customer-360-fixture.ts` creates synthetic native records and dedicated test principals. Independent fixture chains run four at a time and drain before the next group. No existing expectation or timeout changes. The separate `customer360FinanceFixture` adds a company-scoped Finance reader and two synthetic accounts with distinct mappings and two retained native observations each. One mapping changes without changing its version, exercising the exact snapshot-hash refusal. The added Finance test compares the full DTO and JSON, requires both account IDs in a non-Restricted/non-Unavailable section, and checks the current balance, stale balance refusal, ordered history and `context_error`. Existing fixture functions and test bodies remain unchanged.

`tests/unit/customer-page-permissions.test.ts` checks the full permission key, request lifetime and separate native row annotations. The cases in `tests/unit/proof-request-scope.test.ts` exhaust the ordinary cap, then prove late workspace events survive while unrelated events remain suppressed and raw IDs are absent. The review follow-up places a workspace event exactly at the 60,000-event boundary: the marker is emitted exactly once and that event is retained. A separate ceiling permits at most 120,000 additional workspace events, then stops (180,001 records including the marker). These limits remain opt-in, synthetic and diagnostics-only. An added Customer 360 adapter test proves one failed 50-entry chunk does not reject the next chunk; the unchanged Activities adapter unit suite still passes.

The representative fixture is the normal seed plus `customer360Fixture(40)`, with one native Draft quotation per estimate. The larger fixture is the final equality test’s 101 chains plus 100 additional revisions of its first estimate. Each before/after pair reads unchanged synthetic business data. Establish coordinator sessions outside the measured interval and warm each compiled route once. Pin both application servers and PostgreSQL to CPU 0, enable `log_min_duration_statement=0`, and call `GET /api/v1/customers/50000000-0000-4000-8000-000000000001/workspace` serially on main and the branch. Sum PostgreSQL parse, bind, execute and simple-statement durations timestamped inside each GET, excluding measurement-control SQL. Count execute plus simple statements once; parse/bind log entries are separate. Restore logging and the original effective CPU affinity afterwards. This follows [Claude’s compiled-server, single-core, database-log method](https://github.com/deanrfiedler-gif/powerplants-one/pull/707#issuecomment-6652225470).

The representative sample reduces statements by 94.8% and wall time by 42.6%. Summed database duration increased in that sample and decreased slightly in the large fixture. Concurrent query intervals can overlap and exceed request wall time; this is elapsed database duration, not a CPU measurement. These are single warmed local samples with SQL logging, not hosted-load or whole-application targets.

Longest individual statements include their parse, bind and execution phases, correlated by PostgreSQL backend PID within the same GET interval. The original reviewed-head maxima were **98.208 → 259.349 ms** (representative) and **393.742 → 1,462.378 ms** (large fixture). The latter exceeded the review threshold of one second; the slowest statement was a Project lookup batch, principally its bind/planning phase. After reducing only Customer 360 chunks to 50, the remeasured maxima are **408.755 → 726.117 ms** and **386.296 → 689.889 ms**, respectively. Every final maximum is below one second; the largest is 7.3% of the existing 10-second statement timeout. A failed statement can still reject its own chunk; the new unit case proves a failure in the first 50 entries does not reject the next 50. No timeout changes. Both old and new figures are retained with the same-data measurements.

Compiled responses match after removing observation timestamps and comparing decoded continuation bodies: separate compiled processes have separate random cursor-signing keys. The database proof above compares the complete original DTO and JSON, including the exact signed cursor, in one process.
