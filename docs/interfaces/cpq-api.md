Commands include `schema_version: 1`, a caller-generated UUID `operation_id`, and a meaningful `reason`. Mutations return the existing OperationReceipt (`record_id`, `record_version`, `state`, `accepted_at`, `receipt_id`, `task_ids`, `warnings`). HTTP 201 is a first accepted write; 200 is an exact replay. Retain the original payload and operation ID when the response is uncertain. Reuse with different content returns `OperationConflict`. All current permission and source checks happen before recovery returns a receipt. `CpqChanged` outbox events contain identifiers, never pricing or rule payloads; no external dispatch is added.

## Permissions and state transitions

All CPQ calls require `shared.read` and `cpq.read` in the current company; `cpq.read` includes costs and rules. `cpq.author` creates immutable draft revisions; `cpq.review` records review; `cpq.publish` activates an approved release; `cpq.calculate` creates/adopts calculations. Only Company/Workspace grants are accepted. No seed grants these duties. Use the existing independent local access-request workflow to assign approved test roles. Hosted users gain no CPQ duty from the migration.

Calculation and adoption also require current native estimating ownership, `estimating.read`/`estimating.edit`, source visibility and a selected Active option with Complete discovery. An independent reviewer cannot edit the estimate merely because they have a CPQ review duty.

Schema-1 release roots retain Draft → Reviewed or Rejected → Published. Design schema 3 adds an explicit Sealed state: Draft → Reviewed → Sealed → Published; Rejected content must be revised. Seal requires the exact independently approved revision and a third actor. Sealing does not change the company head; activation is a separate command. Appending a revision returns the root to Draft and never rewrites the active historical revision. A run is permanently Ready or Blocked. Later edits produce a new run with a parent pointer. A Ready run can become stale without changing its historical result; adoption rechecks the current basis.

## Definition and input shape

Authoritative TypeScript DTOs are `src/cpq/types.ts`; strict semantic validation is `src/cpq/validation.ts`. Executable synthetic examples are `tests/helpers/cpq.ts`. Unknown fields are rejected.

- Definition: schema 1, label, currency AUD, fact dictionary, component/price definitions, material/labour rules, constraints, and at least one independent expected-result fixture. A release is limited to 60 KB; HTTP commands to 64 KiB except the bounded rebase/receiving decision routes below.
- Facts: stable lowercase key, meaningful label/unit, Decimal/Boolean/Choice type, explicit required flag, allowed choices. Decimal values are strings. Missing values normalize to null; null never means zero or false. Stable instance UUIDs keep generated target identities across recalculation.
- Conditions: ALL/ANY with items, NOT with item, or EQ/NE/GT/GTE/LT/LTE with a registered fact and typed literal. Conditions are bounded to eight levels and 100 nodes. Boolean and choice values support EQ/NE only.
- Parts: key, description, category, unit, resolver, explicit source, validity interval and strictly increasing minimum-quantity price tiers. Validity is checked against the explicit pricing date, not a claim of current market freshness. No live ERP lookup is implied.
- Rules: stable key, description, phase, condition, part, quantity expression and integer priority. Expressions allow registered numeric scalar names, literals, parentheses and `+ - * /` only. Labour may use `bom_<part_key>` for the resolved quantity of that material part, preserving its declared unit; quantities in different units are never implicitly summed. Result quantities use the native three-place quantity contract; money uses exact decimal arithmetic and native rounding.
- Constraints: a typed applicability condition, required condition and actionable diagnostic. Unknown applicability or requirement is a blocker.
- Calculation input: pricing date, one to twenty labelled instances with fact values, and up to 100 overrides. Each override has stable target, exact generated basis hash, Quantity/SellPrice/Suppress kind, value (null for suppression), and reason. A changed basis or missing target blocks adoption. Revoke an override by omitting it from an explicitly reasoned new run; history retains the previous run.

Expose the restricted quantity editor only to rule authors. Estimators should receive labelled controls, optional/unknown states, units and choices. Keep UUIDs/hashes in evidence drawers and API state, not ordinary user-facing input fields.

## Error and recovery UX

### Design schema 3 additions

Schema 1 retains its accepted fields and serialised results. Schema 2 is the opt-in published Product profile described below; it retains schema-1 arithmetic. Schema 3 does not accept Product bindings. A combined design/mapping profile remains separate. Schema 3 adds the following explicit fields; unknown fields still fail validation.

- Facts: Integer/Text, description, System/Global/Shared scope, authored source, minimum/maximum and optional registered discovery `binding.question_id`. Bound values are read from the selected discovery and cannot be overridden by the browser. Integer rejects fractions. Instance `not_applicable` lists only optional null facts; it is distinct from unknown.
- Conditions: `ALWAYS`, `KNOWN`, `NOT_APPLICABLE` and typed `IN`, plus the existing boolean/comparison operators. Empty groups remain invalid. Formulas add exact `ceil(x)`, `floor(x)`, `min(a,b)`, `max(a,b)` and `round(x,places)` with an integer precision of 0–12 (omitting places retains whole-number rounding); signed ties round away from zero. All arguments count toward the existing token, depth and evaluation budgets. Per-rule parameters have stable keys, labels, exact values and units. Arbitrary code/external lookups remain impossible.
- Parts: optional scope `{kind: System|Shared|Configuration, group_fact}`. Shared requires a Text/Choice grouping fact and resolves once per group; Configuration resolves once. Shared facts that disagree become unknown, never an arbitrary first value. Labour BOM references must use material parts in the same output scope. Decision tables govern System rules only. Missing shared groups block. Frozen `price_context` records book, policy, source currency, source-currency units per AUD and recorded instant; each tier includes source unit cost and validates its rounded AUD conversion. Future/expired price evidence blocks use.
- Design: option sets and typed availability, acyclic component structure, shared capacity grouped across systems, UNIQUE/PRIORITY decision tables and pricing policy. Known-value table coverage enumerates exact boundaries, valid integer/range partitions and equality classes, capped at 256 partitions. Unknown runtime inputs still block; coverage is not a general satisfiability proof. Explicit milestone proposals retain condition, anchor, signed offset (±365 days) and BusinessDays/CalendarDays. No calendar date is fabricated.
- Results: condition/rule traces, resolution contributions (including non-winners), calculated/effective quantity, excluded/conflicting/needs-review line states, selected price tier, options, capacities, table outcomes, pricing basis and milestone proposals. Separate configuration, pricing and adoption readiness explains why a proposed price can require ES-05 approval while the saved estimate handover is available. All original evidence is hashed.
- A stale schema-3 adjustment remains effective and visibly Needs review, blocking use. Explicit rebase resubmits its value/reason with the current basis hash; restore removes it in a newly saved evaluation. Schema-1 stale behaviour remains unchanged. Missing targets retain orphan diagnostics.

## Published Product profile — schema 2

The [architecture decision](../decisions/cpq-published-products.md) adopts the reserved schema 2 after inspecting the unfinished local proposal and current main. Use the schema-1 definition/input contract with `schema_version: 2` and an optional `parts[].product` on selected Product components. At least one component must be bound. Schema 1 and schema 3 keep their original strict shapes and hashes; schema 2 does not accept schema-3 design fields. No UI authoring change is included.

A Product binding is `{product_id, revision_id, content_hash, relationships}`: native Variant UUID, exact immutable revision UUID/hash, and zero to ten distinct optional relationship references `{id, content_hash, review_id}`. Omitted relationships normalise to an empty list. Labels, Family/Model identities, latest aliases, mismatched units and bindings on Labour/Freight/Engineering/Subcontract parts are refused. Unbound parts retain authored provenance only. No quantity conversion or Product price lookup occurs.

Products `products.read` plus existing company/workspace authority is required alongside CPQ/native permissions. Save/approval/activation, calculation basis/live preview/save and new adoption recheck every bound component against the exact current published revision, including components that produce no line. Draft successors leave the previous publication valid. Withdrawn, unpublished, inaccessible or superseded sources cannot support new use. The same workspace transaction lock serialises Product commands and CPQ calculation/adoption. Restoring publication never silently substitutes a different revision.

Selected relationships must connect this component's exact revision to another explicitly bound revision, in the same company, with exact retained content hash and independent Conditional review. The catalogue's existing criteria validation applies. CandidateReplacement, Unresolved, Rejected or missing review is refused. Any relationship successor requires a new deliberate reviewed mapping. Conditions, limitations, criterion evidence/owner, source revision/date and review remain explicit; the backend does not infer application suitability from these conditional statements.

Saved `binding.products` contains technical content, stable provider/entity and parent IDs, exact revision, publication event/purpose/audience/effective-context date and relationship evidence. The run content hash covers this snapshot; result/override basis hashes also cover the authored exact binding through the definition/part. Run reads, live previews and adoption previews expose `product_provenance` keyed by exact native line ID/target/basis hash. `availability` and `supplier_lead_time` are always Unknown; `compatibility` is NotAssessed or ConditionalEvidence. Publication, lifecycle and a Ready calculation are not stock or installation approval.

Native adoption keeps cost-line and quotation shapes unchanged. Its immutable adoption row links exact run/result and generated lines to the exact estimate version, and its audit retains Product provenance. The exact-version internal provenance endpoint verifies that chain and rechecks current native/CPQ/Product access. Manual successors are not automatically assigned a new adoption; inspect the original adopted version. Customer-safe quotation output excludes catalogue/source/relationship evidence and internal prices.

`CpqProductVariantRequired`, `CpqProductUnitMismatch`, `CpqProductEvidenceChanged`, `CpqProductPublicationChanged`, `CpqProductRelationshipMismatch`, `CpqProductCompatibilityReviewRequired` and `CpqProductRelationshipSuperseded` are explicit HTTP 409 review/refusal outcomes. `RecordUnavailable` remains the non-disclosing access/missing/cross-company outcome. Retain the proposal, show the exact reason and require a newly authored/reviewed release and calculation when mapping changes. No automatic remap or silent price refresh occurs.

Historical reads and original completed-command recovery recheck current access but do not require current publication. A completed calculate/adopt/save/review/activate replay returns its original receipt after withdrawal; it does not repeat adoption. Access loss blocks both reads and recovery. Existing override rebase, manual-owned-line conflict, receiving limit, original operation ID and atomic rollback contracts remain in force.


## Governed cost and labour profile — schema 4

[Decision](../decisions/cpq-governed-costs.md) records the opt-in schema and existing persistence choice. Schema 4 combines schema-1 calculation rules with optional schema-2 Product bindings and at least one `parts[].cost_source`. Schemas 1/2/3 are unchanged. This profile does not combine schema-3 design authoring. All command envelopes remain schema 1.

A Product or Labour part may carry `cost_source` with native `source_id`, exact `revision_id`, `content_hash`, `review_event_id`, positive `source_version`, native `reference`, positive revision number `revision`, and normalized `content` from the existing exact Cost Source read. The server verifies all evidence against the same-company immutable revision and independent Reviewed event. No label/latest lookup grants provenance. Existing Cost Source `estimating.read` company authority is required alongside CPQ duties on save, fixture preview, review, activation, run reads and receipt recovery; Products read remains required when technical Product references are included.

Bound parts keep the existing authored sell tiers and sell-validity interval. Every authored `tiers[].unit_cost` must be `0.00`, an explicit unused marker; no fallback is permitted. The source supplies unit cost using the resolved native three-decimal quantity, including quantity overrides. Direct synthetic AUD/ExcludingTax source content only; no unit conversion, FX or landed-cost adaptation. Source effective/expiry dates are checked against the explicit calculation `pricing_date`, not a moving clock. Unknown expiry stays a visible warning, matching the existing source contract. Below-minimum, expired/not-yet-effective and below-cost selling prices produce Blocked results with the native diagnostic.

New-use checks compare the exact source header version at save, approval, activation, basis preparation and adoption, including declared sources not generated in this run. A draft/review/successor change yields `CpqCostSourceChanged`; mismatched evidence yields `CpqCostEvidenceChanged`; absent exact independent review yields `ReviewedSourceRequired`. Current access loss yields the native unavailable response. No withdrawal state is invented for Cost Sources. Explicit historical reviewed selection remains supported when a new binding acknowledges the current source header. Historical reads and original-operation retries do not require freshness; they retain current authority and exact hash checks.

Schema-4 calculations report engine `PPO-CPQ-4`. The immutable run's `binding.cost_sources` retains each exact source snapshot plus part key and review attribution. Each generated `result.lines[].cost_source` records native line/source/revision/review IDs, pricing date, selected minimum quantity/unit cost and validity warning. Live preview, saved run reads and adoption preview also return `cost_provenance`, joining the selection to its full retained source snapshot. Customer output must never expose this internal evidence.

Adoption writes the exact native `estimate_cost_source_bindings` in the same transaction as the new version, CPQ adoption, audit, outbox and receipt. Existing estimate reads return these typed `source_bindings`. Manual lines and their bindings are retained; generated bindings are replaced explicitly, including when a source or quantity changes. Current saved Product and Cost Source evidence is checked before comparing the active basis. Original-operation recovery still runs before freshness checks.

To refresh, author/review/activate an explicit successor release, then calculate with `parent_id` referencing the original run. `/compare` shows exact source selections in before/after lines and cost, sell, difference, margin and markup totals. Source changes invalidate override basis hashes; the caller must review or revoke those overrides. Adopt only the exact new preview. There is no automatic price refresh, new selling policy or new UI in this increment.

Governed schema-4 calculations must use a pricing date in the native binding range 0001-01-01 through 9998-12-31. `CpqCostPricingDateRange` blocks out-of-range results before adoption readiness. This reuses the existing persisted source-binding constraint; it does not change schemas 1–3 or historical result bytes. Source effective/expiry checks still apply independently.

Governed source validity dates also require year 0001 or later (`CpqCostSourceDateRange`), because the native binding guard casts these retained JSON dates to PostgreSQL dates. Year-zero source validity blocks calculation readiness independently of the selected pricing date.

## Explicit override rebase and receiving resolution — workflow version 1

The four POST rebase/receiving preview and command routes accept at most 512 KiB of UTF-8 JSON, accommodating 100 override or 200 receiving decisions with 500-character reasons. Rebase `input` independently remains limited to 64 KiB of serialized UTF-8 JSON (`InvalidData`, field `input`). Oversized request bodies return `PayloadTooLarge` after bounded discard. A 1 MiB discard ceiling and ten-second deadline protect transport; extreme or stalled uploads may close at those hard limits. Other routes retain their existing limits.

[Decision](../decisions/cpq-rebase-conflicts.md) and [execution evidence](../testing/evidence/cpq-rebase/README.md) cover this bounded BC-04 / ES-02 / ES-03 increment. The envelope version is independent of definition schemas 1–4. No definition schema, migration, grant, dependency or pricing policy is added. Existing evaluation/result hashes and original-operation payloads remain valid. New legacy adoption attempts also refuse unacknowledged obsolete removals; historical accepted estimates and receipts are unchanged.

Rebase preview accepts `{revision_id,input,decisions}` on the exact parent run. `revision_id` is the selected Complete discovery revision; the active company release supplies the new rules and current Product/cost authority. `input` has the ordinary calculation shape with `overrides:[]`. Every prior override requires one decision:

```json
{"source_target":"c0860000-0000-4000-8000-000000000001:sensor:each","kind":"Quantity","action":"Keep","target":null,"value":null,"reason":"Retain the reviewed quantity on the current basis"}
```

Use the exact target supplied by the saved result, never construct it from labels. Actions are Keep (same target/value), Replace (same target, explicit new decimal `value`), Remap (explicit compatible target in `target`, same value) and Revoke (omit from successor). `target` must be null except for Remap; `value` must be null except for numeric Replace. Suppress retains null. Kind remains Quantity, SellPrice or Suppress. Each source target/kind pair occurs once, with a reason; maximum 100 decisions. Remapping requires matching native category and unit. Missing targets, incompatible units, duplicate destinations and fabricated decisions cannot be saved. Material choices are applied before calculating labour override bases; shared/configuration targets use the evaluator's exact identity. Three evaluations share the existing five-second worker budget.

Preview returns the exact parent hash, current binding/hash, normalized decisions and effective input, baseline/result, available target bases, unresolved decision codes, `ready` and `preview_hash`. Workflow `ready` means all decisions are resolved; `result.ready` separately reports calculation/adoption eligibility. A successor may therefore be saved as Blocked under the existing run contract. Save supplies the same proposal plus command envelope, new run `id` and `preview_hash`; it recalculates under the workspace transaction lock. `CpqRebasePreviewChanged` refuses changed confirmation; `CpqRebaseDecisionsRequired` refuses incomplete decisions. Current discovery, source publication and cost-authority errors retain their established meanings. The saved run's `binding.rebase` records workflow version, exact parent ID/content hash, preview hash and decisions, covered by its outer content hash. Current basis comparison excludes only this typed workflow evidence. No old run is updated.

Receiving preview accepts `{decisions:[{line_id,action,reason}]}`. Actions are Keep, Replace or Remove, with at most 200 distinct previously tracked CPQ line IDs. Unrelated manual lines cannot be targeted. The preview records exact prior/current/proposed line snapshots and identifies Changed, Removed, Obsolete, RetainedDecision or Unchanged states. Every state other than Unchanged requires a decision. Keep requires a current line and preserves it exactly; Replace requires a generated line and receives that exact line; Remove explicitly deletes or acknowledges an absent line. Previously kept or deliberately omitted generated targets remain protected against later replacement/recreation until explicitly decided again. Removal evidence remains protected even when intervening releases also omit the target; a later reintroduction still needs explicit Replace. Already absent targets need no repeated decision while they remain absent. An explicit Replace without a generated target is refused.

The response includes `ready`, `unresolved`, normalized `resolution`, retained/generated/received lines and before/calculated/receiving totals. `CpqOwnedLineChanged`, `CpqRemovalReviewRequired`, `CpqReplacementMissing` and `CpqCurrentLineMissing` identify unresolved choices. Identity collision with an unrelated manual line is refused. This resolution workflow requires one to 100 received lines (`CpqReceivingLinesRequired` refuses an empty resolution). Existing native unit, decimal, AUD and sell-not-below-cost contracts still apply. Removing every line is not an empty-estimate workflow; legacy calls with no resolution history retain their prior empty-line behavior. The combined generated and retained identity history is bounded to 200 targets; `CpqRetainedHistoryLimit` refuses overflow without discarding past removals.

Adoption adds optional `resolution:{decisions:[...]}` to the existing command. The preview hash binds the decisions, line snapshots and current estimate version; changed choices or intervening edits need a new calculation/preview. The command writes native version, source bindings, adoption, resolution audit, outbox and receipt in one transaction. Older calls without `resolution` also persist carried removal evidence when no new decision is required; their original input/receipt shape stays valid. Its adoption row contains only generated lines actually received. Normal native binding inheritance applies to kept lines: changing quantity, unit, cost or source basis can remove an inherited cost binding under the existing estimate contract. Keeping a manual line never asserts that it uses the successor's Product/cost basis.

Exact Product provenance returns `ResolvedAdoption` for this opted-in workflow, with `product_provenance` for received generated lines and separate `retained_history` for ManualRetained or ExplicitlyRemoved lines. Historical attribution names the original run and original Product evidence and checks current access to every referenced run. Original exact adoptions retain `ExactAdoption`; unrelated versions retain NoCpqAdoption. All internal resolution, cost, margin and source evidence stays outside customer-safe quotation projections.

Keep the original operation ID and normalized payload after uncertain outcomes. Exact command replay and `/operations/:id` recheck current authority, including retained origins, before returning the original receipt. Historical recovery does not reapply the decisions or demand that the old source remains current. A new use still rechecks all publication, cost, ownership, basis and native receiving guards. UI controls, automatic target matching and operational acceptance remain separate.

## Release quality and exact impact review — workflow version 1

[Decision](../decisions/cpq-release-quality.md) and [execution evidence](../testing/evidence/cpq-quality/README.md) define the bounded BC-04 increment. Definition schemas 1–4, saved engine/result hashes and existing receipt payloads remain unchanged. Quality evidence uses accepted immutable `CpqRelease` audit records; there is no new migration, capability, price policy or customer DTO.

| Method | Path | Input | Result |
|---|---|---|---|
| GET | `/cpq/releases/:id/quality` | No query fields | `expected_version`, `enrolled`, `latest_assessment`, exact current `report` and `report_hash` |
| GET | `/cpq/releases/:id/quality?assessment_id=UUID` | Exact native audit-event ID | Historical immutable `assessment` and its retained independent `review`; current source access still required |
| POST | `/cpq/releases/:id/quality/assess` | Existing schema-1 command envelope, `expected_version`, `report_hash` | Atomic accepted assessment, release command-version increment and original receipt |
| POST | `/cpq/releases/:id/quality/review` | Envelope, `expected_version`, `assessment_id`, `report_hash`, `outcome: Approved or Rejected` | Atomic independent exact-impact decision and original receipt |

All requests retain existing private/no-store, origin, working-company and 64 KiB request limits. Assess needs `cpq.author`; review needs `cpq.review`; publication retains `cpq.publish`. Every report also requires current native estimate/discovery/opportunity and Product/Cost Source read authority for all referenced sources. CPQ authority does not confer these permissions. An inaccessible member refuses the whole report with `RecordUnavailable`; there are no hidden-row counts or purported complete partial reports.

The first accepted assessment **permanently enrolls the release root**. Every subsequent revision of that root requires impact approval before activation, including calls through the existing activation endpoint. Reading does not enroll; no unenroll command exists. Roots with no assessment retain legacy publication behavior. Expose `enrolled` plainly in future authoring controls; do not claim that legacy roots have impact approval. Assessment/review increments the existing release command version but leaves the immutable definition and ordinary Draft/Reviewed/Sealed/Published state unchanged. Schema-3 ordinary sealing remains required.

`report.schema_version` is 1. Candidate and current active baseline retain exact revision/content and activation identities. `members` identify actual frozen definition fields by kind/key/content hash; `rule_members` retain native schema-3 version IDs. Existing Product and cost snapshots remain exact. `fixtures` are the candidate's executed expectations; `baseline_regression` replays active fixtures against the candidate and exposes intentional changes. `changes` reuses semantic comparison. `coverage.scope=ObservedFixturesOnly` reports contributing fixture indexes and schema-3 observed outcomes/table partitions; it never claims all-input coverage. `conflicts` keeps diagnostics visible, including intentionally expected negative cases. `approval_eligible` requires passing candidate fixtures and complete, conflict-free table partitions. Baseline expectation changes, unobserved rules and blocked estimate simulations remain explicit review evidence.

`affected_estimates` covers every open CPQ-backed estimate in the company, including manually saved successors of the latest adoption. Open means Active option, Draft workspace and Draft commercial group under the existing receiving boundary. Each entry binds current native version/hash/lines/totals, latest adoption, exact source run/hash, previous calculation and candidate simulation with original inputs/overrides. `line_changes` compares original generated lines with candidate generated lines; `current_native` separately preserves manual changes. `receiving=ExplicitRebaseAndAdoptionRequired`: simulation neither adopts lines nor resolves stale overrides or manual edits. Later adoption remains separately confirmed under its existing guards. Quotations receive none of this internal evidence.

A complete report is limited to 25 open estimates, 2 MiB combined worker input and 2 MiB report evidence. `CpqQualityLimit` explicitly refuses overflow; no truncation or partial approval. Computation uses the existing five-second isolated worker and memory budget (`CalculationLimit` on failure/timeout). These synthetic bounds are not production latency targets.

Assessment re-derives the report under the shared workspace mutation lock and refuses a changed preview with `CpqQualityChanged`. Independent approval requires the latest assessment of the current revision and exact hash; the reviewer differs from both revision author and assessment author. `CpqIndependentQualityReview` refuses self-review, `CpqQualityFailed` refuses failed fixtures/table coverage, and `CpqQualityAlreadyReviewed` preserves a final decision. A rejection requires explicit reassessment before another decision.

Activation of an enrolled root requires the latest Approved assessment, unchanged current report and current reviewer duties/source access. `CpqQualityReviewRequired` refuses missing, rejected or superseded approval; `CpqQualityChanged` refuses changed activation, current native versions/population or source basis. Existing Product/Cost Source refusal codes are retained. `CpqIndependentQualityPublication` requires the publisher to differ from impact author and reviewer, in addition to existing ordinary review/publication segregation. Activation audit retains exact assessment/review IDs and report hash. No newer source is substituted.

Historical reads and original assess/review/activate recovery authorize every accepted source before returning its original evidence/receipt, without requiring yesterday's population or publication state to remain current. Reuse the original operation ID and payload after an uncertain result. `GET /operations/:operation_id` remains actor-bound. A replay never creates a second assessment, decision or activation.

The owned package workflow below extends this report with versioned rule/table ownership and synthetic workload evidence. Operational fixture families and performance targets, native controls and live integration remain separate work. This report does not assert stock, supplier lead time, tax, exchange rates or operational acceptance.

Input compatibility is checked with the existing calculation-input validator before replay. A removed fact, changed type or incompatible schema-3 field produces `input_status=NeedsInputReview`, exact validation fields, `simulation=null` and `line_changes=null`; it never masquerades as a valid zero-cost calculation. Baseline fixture replay likewise records incompatible input as a failed regression with no result hash. Successful replay hashes the actual candidate definition, not a definition modified to contain the old fixture list.


## Owned rule and table packages — workflow version 1

The [package decision](../decisions/cpq-rule-packages.md) implements the next BP-04 / BC-04 / ES-02–03 boundary. Definition schemas 1–4 and their hashes are unchanged. Package content/workflow version 1 and the optional immutable `package_manifest` are separate contracts. Prices continue through existing authored tiers and schema 4 Cost Sources. Table packages use schema 3; no cross-schema conversion is inferred.

| Endpoint | Behaviour |
| --- | --- |
| `GET /api/v1/cpq/packages?company_id=UUID` | Company-authorised package root list, at most 100, ordered by native ID. |
| `POST /api/v1/cpq/packages` | Save an immutable revision; common operation envelope plus `id`, `company_id`, `kind` (`Rules` or `Tables`), `expected_version` (zero for creation), and `content`. The creator becomes the permanent package owner. |
| `GET /api/v1/cpq/packages/:id` | Current root, exact current revision, retained revisions and events; current authority over every retained Product/Cost Source is required. Unknown query keys refuse. |
| `POST /api/v1/cpq/packages/:id/attest` | Recorded fixture owner runs and acknowledges the exact current revision's fixtures and workload targets. Common envelope, `expected_version`, `revision_id`, `content_hash`. Stores `Tested` or `TestFailed` evidence. |
| `POST /api/v1/cpq/packages/:id/review` | Same exact basis plus attestation `evidence_hash` and `outcome` (`Approved` or `Rejected`). Reviewer must differ from both owners. |
| `POST /api/v1/cpq/packages/:id/publish` | Same exact basis plus approved review `evidence_hash`; publisher differs from both owners and reviewer. |
| `POST /api/v1/cpq/packages/:id/withdraw` | Owner with current author permission withdraws the exact current revision, preserving all evidence. |
| `POST /api/v1/cpq/packages/compose` | Read-only assembly preview: `company_id`, normalized rehearsal `definition` and exact `packages`. Returns assembled definition/hash, manifest/hash and exact references for release save. Package members replace the preview template's rules/tables explicitly. No receipt or release is created. |

Package content is `{schema_version:1,label,definition,member_keys,fixture_owner_id,workload}`. Member keys select unique actual rules or decision tables from the complete existing definition used as rehearsal context. A member's native identity is `(package_id, revision_id, key)`; its content hash distinguishes unchanged/revised bytes. Company, kind and package owner cannot change. Fixture ownership is versioned; assignment grants no permission and does not count as acknowledgement. Save/attest/withdraw reuse `cpq.author`, review uses `cpq.review`, and publication uses `cpq.publish`, always with company `cpq.read` and current source authority. A distinct fixture owner can require four different people overall. No new capability or seed is added.

`workload` contains `family`, `rationale`, integer `evaluation_ms` (1–1000), integer `result_bytes` (1024–2000000), and `cases:[{fixture,role:Small|Typical|Boundary}]`. Every fixture is named exactly once, all three roles must occur, and three to six fixtures are required. Targets and fixture responsibility are immutable revision content. Three samples per fixture measure evaluation time inside the unchanged five-second isolated worker, serialized result bytes, lines, instances and input bytes. The attestation records actual fixture results, table coverage, all samples, runtime version, target basis and `SyntheticInWorkerEvaluation` scope. Failed fixtures, coverage or targets retain failure evidence and block approval. This is neither end-to-end API latency nor an operational SLA. The declared family/rationale is the fixture owner's synthetic scope statement, not proof of a representative business workload. Content and complete attestation reports are each capped at 150000 JSON bytes; save and composition requests at 200000 bytes. An oversized report refuses with `CpqPackageLimit`, without retaining partial evidence. Worker failure/time-budget refusal creates no partial accepted event.

Release save optionally accepts `packages:[{package_id,revision_id,content_hash,publication_id}]`, at most 20, unique and canonical by package ID. All candidate rules and schema 3 decision tables must match selected members exactly once. Missing, overlapping, altered and extra members refuse. Schema, facts, constraints, technical part shapes and non-table design contracts must match rehearsal context. Prices may continue to use existing contracts, but every selected package's fixtures must pass against the complete candidate, including its actual prices. The manifest freezes publication, member hashes, package owner, fixture owner and evidence hash on the immutable release revision. Package governance cannot be removed from subsequent revisions of that release root. Package-bound activation requires the existing exact independent quality/impact assessment even before an assessment has been explicitly created.

New save, release review/seal/activation, calculation, rebase and adoption check current exact package publication, unchanged revision and the continuing authority of owners, reviewer and publisher. Changed, withdrawn or superseded packages return `CpqPackageReviewRequired`; lost authority uses the existing non-disclosing `RecordUnavailable` contract. No newer package or Cost Source is substituted. Run `binding.packages` freezes the manifest and participates in the run hash. Receiving audit retains `cpq_package_provenance`; native estimates retain the exact run chain, including manual/override safeguards. Customer quote projections exclude package owners, fixtures, targets and internal source evidence.

All package operations use original operation IDs, workspace serialization, expected versions, immutable events, audit, receipts and outbox in one transaction. `GET /operations/:operation_id` and exact command retry reauthorise the original sources and return the original receipt after withdrawal/supersession; they do not rerun workloads or republish. Payload changes under an accepted operation ID conflict. Historical releases, runs, estimates, quality reports and receipts keep their original hashes and source authority rules. Migration 0102 installs empty package tables and a nullable manifest column, with closure/immutability and native identity guards; no historical rows, grants or seed receipts are rewritten.

Native release insertion also checks the complete package snapshot and ordered member hashes against the exact retained rule/table bodies. Empty, forged, reordered or extra snapshot fields refuse atomically before immutable history is created. Member hashing uses the normalized rule/table contract; it is not a general-purpose JSON floating-point serializer.
